## 2. Namespaces: die drei Fallen von Tailwind v4

In v4 erzeugt ein Theme-Token nur dann Utilities, wenn es im **richtigen** Namespace steht.
Ein falscher Präfix wirft **keinen Fehler** — die Tokens sind einfach stumm. Drei Fälle,
die in der ersten Fassung von `app.tcss` genau so passiert sind:

| Zweck | ❌ falsch | ✅ richtig | erzeugt |
|---|---|---|---|
| Schriftgröße | `--font-size-16` | `--text-16` | `text-16` |
| Breite | `--width-btn-max` | `--container-btn-max` | `w-`, `min-w-`, `max-w-`, `basis-` |
| Höhe | `--height-btn-lg` | *kein Namespace* → `@utility` | `h-btn-lg` |

`--font-*` ist ausschließlich die **Schriftfamilie**, nicht die Größe. Für Höhen existiert
in v4 kein Theme-Namespace — die Werte bleiben normale Custom Properties und werden per
`@utility` freigegeben.

**Merksatz:** Nach jeder Token-Änderung einmal bauen und im Output prüfen, ob die Klasse
wirklich existiert. Stumme Tokens fallen sonst erst im Layout auf.

## 3. Aufbau der Datei

```
1. Primitives            :root                      Rohwerte
2a. Color Modes          :root + 4 × [data-theme]   global themebar
2b. Single-Mode          :root                      Filter Panel, Search, LG/Inline
2c. Lively Themes        :root + [data-lively-theme] Mega-Cards, LG/Primary
2d. Heights              :root                      Basis für @utility
3. @theme inline         Farben → Utilities         laufzeit-umschaltbar
4. @theme                Text, Spacing, Container   statisch
5. @utility              Höhen
```

`@theme inline` ist bei den Farben **Pflicht**: nur so geben die Utilities `var(--…)` aus und
bleiben zur Laufzeit über `data-theme` umschaltbar. Ohne `inline` friert v4 die Werte beim
Build ein. Für die statischen Skalen (Text, Spacing, Container) ist normales `@theme` besser —
dann werden die Variablen zusätzlich als CSS-Variablen ausgegeben und sind in handgeschriebenem
CSS nutzbar.

## 4. Die 4 Modi — Blöcke müssen VOLLSTÄNDIG sein

Die vier Figma-Modi werden zu vier `data-theme`-Werten:

```
cole-tint-surface-warm    (Default)
cole-tint-surface-snow
purple-tint-surface-warm
purple-tint-surface-snow
```

**Regel: jeder Block deklariert alle 55 Tokens — keine Diffs.**

Keine Stilfrage, sondern Voraussetzung für das lokale Überschreiben aus 2.2 §3.
Custom Properties **erben**. Ein Block, der nur die Abweichungen gegenüber dem Default setzt,
funktioniert nur, solange sein Elternknoten der Default ist. Sobald verschachtelt wird, erbt
er für jedes nicht erneut gesetzte Token die Werte des Elternmodus:

```html
<!-- mit Diff-Blöcken defekt: Card erbt purple-Textfarben auf snow-Fläche -->
<section data-theme="purple-tint-surface-warm">
  <article data-theme="cole-tint-surface-snow">…</article>
</section>
```

Zweiter Punkt: der Default braucht einen **eigenen Selektor**. Steht er nur auf `:root`, kann
kein Teilbaum zurück auf `cole-tint-surface-warm` geschaltet werden:

```css
:root,
[data-theme="cole-tint-surface-warm"] { /* … alle 55 … */ }
```

Gleiches gilt für beide `data-lively-theme`-Achsen (Default `mc-blue-pistacio-green` bzw.
`lg-purple-warm-white`).

> Die Redundanz ist gewollt. 4 × 55 Zeilen sind der Preis dafür, dass Verschachtelung sich
> genau wie ein Figma-Modus-Pin verhält.

## 5. Spacing: eine Skala statt Box-Spacing und Gaps

In Tailwind lesen `p-*`, `m-*`, `gap-*` und `space-*` **alle** aus demselben `--spacing-*`.
Da Box Spacing und Gaps in Figma pro Stufe identische Werte haben, werden sie im Code zu
einer Skala zusammengeführt — das ist die übliche Lösung, keine Vereinfachung.

| Token | rem | px | Figma |
|---|---|---|---|
| `--spacing-zero` | 0 | 0 | `box-spacing-zero` / `gap-zero` |
| `--spacing-xxxs` | 0,125rem | 2 | `…-xxxs` |
| `--spacing-xxs` | 0,25rem | 4 | `…-xxs` |
| `--spacing-xs` | 0,375rem | 6 | `…-xs` |
| `--spacing-sm` | 0,5rem | 8 | `…-sm` |
| `--spacing-md-sm` | 0,75rem | 12 | `…-md-sm` |
| `--spacing-md` | 1rem | 16 | `…-md` |
| `--spacing-md-l` | 1,25rem | 20 | `…-md-l` |
| `--spacing-lg` | 1,75rem | 28 | `…-lg` |
| `--spacing-xl` | 2,5rem | 40 | `…-xl` |
| `--spacing-xxl` | 3rem | 48 | `…-xxl` |
| `--spacing-xxxl` | 3,5rem | 56 | `…-xxxl` |

`p-md` und `gap-md` ergeben also beide 1rem. Die Trennung in zwei Figma-Collections bleibt
dort sinnvoll (sie filtert den Variablen-Picker auf Padding bzw. Gap) — im Code hat sie
kein Gegenstück.

**Achtung:** v4s dynamische Zahlenskala bleibt aktiv, `p-4` funktioniert weiter und umgeht
die Tokens. Wer das unterbinden will, setzt vor der Skala `--spacing-*: initial;`.

## 6. Breiten & Höhen

Breiten laufen über `--container-*`. Weil Figma pro Komponente **unterschiedliche** min- und
max-Werte hält (z. B. `Cards/Default` 15rem / 24rem), tragen die Token-Namen das Suffix mit —
die Klasse heißt daher `min-w-card-default-min`. Etwas redundant, aber eindeutig.

Höhen brauchen `@utility`:

```css
@utility h-btn-lg { height: var(--height-btn-lg); }
@utility min-h-card-md { min-height: var(--height-card-md-min); }
```

## 8 Bewusst 1:1 übernommene Auffälligkeiten

Diese Werte sehen nach Migrationsresten aus, sind aber **so in Figma** und daher unverändert

## 9. Offene Punkte

### 9.1 Figma-Variablen-Namen

Namens-Audit der Collection `Lyt scl / Tailwind-utility-units` ist durch (27.07.2026),
alle 52 Variablen erfüllen die Regel 1 twuc = 4px. Kein falsch benannter Alias mehr im File.
Die drei Befunde und die Entscheidung „Wert statt Name anpassen" sind in
`2.4-app-tcss-aenderungsprotokoll.md` dokumentiert — dort auch der Methodik-Hinweis zu
**Stale-Namen** aus `getVariableByIdAsync`.

### 9.2 Typografie: noch nicht abgedeckt

- Keine `--leading-*` / `--tracking-*` Tokens, obwohl die 65 Text Styles durchgängig
  eigene Line-Heights und Letter-Spacings tragen. Aktuell nur Familie + Größe.
- `Input/Label SM` (9px) und `Cards/Blog/Title` (19px) haben **keine** Entsprechung in
  `Typografy` — diese zwei Styles sind über die Token-Skala nicht darstellbar.
  Entweder 9 und 19 in `Typografy` ergänzen oder die Styles auf vorhandene Stufen ziehen.

### 9.3 OptionSelection — Farbwerte noch offen

Benennung ist erledigt: Gruppe `OptionSelection/Button`, Leafs `option-selection-button-*`
(spiegeln die Gruppe wieder), passend zur Komponente `Buttons / XS / OptionSelectionButton`.

Die **Farbwerte** stehen so, wie Figma sie hält — Korrekturen daran passieren in Figma,
nicht im CSS.
Im CSS heißen die Tokens `--btn-option-selection-*` (Utilities `bg-btn-option-selection-bg` usw.)
— gleiche Form wie `--btn-primary-*`, `--btn-secondary-*`, `--btn-inline-*`.

**Ableitungsregel Figma → CSS:** `Button-X/button-x-<rolle>-default` → `--btn-x-<rolle>`,
also `button` → `btn` und das Suffix `-default` entfällt. `option-selection-button-bg-default`
ergibt damit `--btn-option-selection-bg`. Größen-gebundene Sets behalten ihr Präfix
(`--lg-primary-*`, `--lg-inline-*`), weil sie auf einer eigenen Achse liegen.

**Achtung bei Umbenennungen:** ein Token-Name steht an drei Stellen — in allen vier
Modus-Blöcken, in der `@theme inline`-Registrierung und auf deren rechter Seite (`var(--…)`).
Wird nur ein Teil umgestellt, ist die Variable nur in manchen Modi definiert und die Utilities
fallen in den übrigen still aus — ohne Build-Fehler. Nach jeder Umbenennung prüfen: kommt der
alte Name nirgends mehr vor, und stimmen Registrierung und Referenz überein?

## 11. Namenskonventionen (Figma → CSS eindeutig halten)

Beschlossen 28.07.2026. Ziel: die Übertragung ist ableitbar, nicht auslegungsbedürftig.

### 11.1 Zustands-Vokabular (geschlossen)

| Suffix | Bedeutung |
|---|---|
| `-default` | Ruhezustand |
| `-hover` | Hover |
| `-focused` | Feld hat den Fokus, wird benutzt (Inputs, Search) |
| `-selected` | ausgewählt |
| `-selected-hover` | ausgewählt **und** Hover |
| `-inactive` | löst keine Aktion aus |
| `-hover-&-click` | ein Token deckt Hover **und** Klick ab |

Das Präfix `on-` entfällt (`-on-hover` → `-hover`). Deckt **ein** Token zwei Zustände ab,
gilt die `&`-Schreibweise in fester Reihenfolge: `-hover-&-click`.

**`-inactive`, nicht `-disabled`:** der Button bleibt klickbar und gibt eine Fehlermeldung
zurück — er ist also nicht technisch deaktiviert. `-disabled` würde das Verhalten falsch
beschreiben; es wird nur verwendet, wenn wirklich das HTML-Attribut gemeint ist.

**`-focused`, nicht `-active`:** ein Feld in Benutzung entspricht `:focus`. In CSS bedeutet
`:active` dagegen „wird gerade gedrückt" — für Inputs also der falsche Begriff. Deshalb kommt
`-active` als eigenständiges Suffix nicht mehr vor; gedrückte Zustände stecken in
`-hover-&-click`.

Abgelöst: `-on-hover`, `-on-active`, `-on-selected`, `-on-selected-on-hover`,
`-on-hover-or-click`, `-on-active-or-hover`.

### 11.2 Property-Vokabular

`bg`, `label`, `stroke` — kombinierte Tokens immer in der Reihenfolge `label-&-stroke`
(nicht `stroke-&-label`). Das `&` heißt: **eine** Variable versorgt zwei CSS-Eigenschaften,
im Code also zwei Utilities aus einem Token.

### 11.3 Modus-Namen: genau eine Achse

Ein Modus-Name kodiert genau eine Dimension. Die LG-Primary-Modi hießen früher
`purple-warm-white`, `yellow-cole-tint` … und mischten Kampagnen-Hue **und** Surface;
jetzt nur noch `purple`, `sky-blue`, `yellow`, `orange` — im CSS
`[data-lively-theme="lg-purple"]` usw.

> **Noch offen:** die Label-Farbe dieser Buttons zeigt weiter auf eine feste Weiß-Stufe
> (`warm-white/100`) und folgt damit nicht der warm/snow-Achse — ein LG-Button in einer
> snow-Section zeigt warmes Weiß. Sauber wäre eine Bindung auf `Surface/surface-color`;
> das ändert die Darstellung und ist daher eine Design-Entscheidung.

### 11.4 Schreibweise

Variablennamen kebab-case, keine Leerzeichen (`peachy coral` → `peachy-coral`).
Gruppennamen dürfen Leerzeichen behalten (`Price Range Filter`) — die Ableitung nutzt den Leaf.

**Keine Zahl im Namen, die dem Wert widersprechen kann.** Bei Abweichung gilt der
**px-Wert**, der Name wird korrigiert (`[twuc]-304 (76rem)` enthielt 1248px = 78rem).

### 11.5 Ableitung Figma → CSS

`Gruppe/leaf-<rolle>-<zustand>` → `--<kurzform>-<rolle>-<zustand>`: `button` → `btn`,
`-default` entfällt, das Kategorie-Präfix bleibt erhalten (es verhindert Kollisionen,
nicht die Rolle). Der Leaf spiegelt weiterhin seine Gruppe.

### 11.6 Gruppen-Ebenen

Genau **eine** Gruppen-Ebene pro Collection, damit jede Variable die Form `Gruppe/leaf` hat.
`OptionSelection/Button/…` war die einzige zweistufige Gruppe; die zweite Ebene trug keine
Information, weil der Leaf `option-selection-button-…` sie schon enthält.

Die Unterscheidung **standardisierte vs. spezialisierte Buttons** bleibt bewusst über die
Gruppennamen erhalten (`Button-Primary/-Secondary/-Inline` vs. `Segmented`, `Counter`,
`OptionSelection`). Ein einheitliches `Button-`-Präfix wäre für die Ableitung ohne Nutzen —
die greift auf den Leaf zu — und würde die Unterscheidung verwischen.

## 10. Die drei Regeln (unverändert aus 2.2 §6)

1. **Keine Primitives in der Komponente** — kein `bg-[#1d2020]`, kein `bg-cole-tint-90`,
   immer das semantische Utility.
2. **Theme am Container** — `data-theme` kaskadiert; Lively Themes und Single-Mode
   laufen pro Komponente.
3. **Die Farb-Logik liegt in den Token-Definitionen, nicht im Markup.** Dasselbe
   Utility funktioniert in allen vier Themes unverändert.
