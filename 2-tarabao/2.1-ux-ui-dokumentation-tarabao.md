## Design System
### Colors System
#### What are Themes?

**Grundregel:** Komponenten binden **nur semantische Tokens**, nie palette-direkt (`cole-tint/90`) und nie hardcoded. Sonst folgt das Element dem Theme nicht.
- Das entspricht dem State-Of-Art. 
- Das erlaubt mittelfristig einfachere und fehlerfreie Pflege des Designs.
- Das ist die Grundlage fürs erweiterte Theming, kompatibel mit Tailwind.

Das Farbsystem des B2C-Shops. Ein **Theme** = eine Kombination aus **Fläche (Surface)** und **Tinte (Tint)**. Ein einziger Umschalter an Frame/Section (Figma) bzw. Container (Code) schaltet Fläche, Text, Icons gemeinsam ins passende Schema. Das Schema der eigenen Komponenten wie z. B. von Buttons schaltet in Figma nicht mit. 

*** Wichtige Regel für Design & Development: die Schriftfarbe der Buttons / Primary passt sich der surface  Farbe an. Hat eine Komponente den Modus cole-tint-surface-snow, so muss der Button cole-tint-surface-snow oder aber purple-tint-surface-snow haben. Der optische Effekt, der dadurch entsteht, ist einer der wichtigsten ästhetischen Pfeilder des Design-Systems

#### 2. Variables Layers in Figma - important (!)
Für die meisten Komponenten mit Ausnahme der Mega Cards und der dazugehörigen Buttons LG sowie der Search und Filter-Komponenten gilt der folgende Aufbau:

```
Clrs (Palette)                → Rohfarben, z.B. cole-tint/90, purple-tint-light/old, snow-white/100
   ↓ aliased
Clrs / Color Modes            → Gruppe "Color Themes/…" mit 4 Modi (die Schemata)
   ↓ gebunden
Komponenten                   → binden DIREKT die Color-Themes-Tokens
```
Semanatische Variables nach Themes für Mega-Cards und Buttons LG finden sich unter 
```
Clrs / Mega-Cards
Clrs / Btns / Large / Primary
Clrs / Btns / Large / Inline
```

**Token-Namen** tragen die Kategorie im Namen, Muster `<kategorie>-<rolle>-<state>`:
`button-primary-bg-default`, `button-primary-label-on-hover`, `input-label-&-stroke-on-active`, `segment-bg-on-selected`, `content-text`, `surface-color` …
States: `default`, `on-hover`, `on-active`, `on-selected`, `inactive`.

**Umschalten in Figma:** Section/Frame auswählen → Appearance → `Clrs / Color Modes`-Modus setzen. 
(!) Eingebettete Komoponenten (Überschriften, CMS-Elemente etc.) übernehmen den Modus, wenn er nicht separat gesetzt wurde.

***Insbesondere für Karten- und Karten-ähnliche Elemente wird er stets abweichen, da anderenfalls keine optische Abhebung mittels Hintergrundfarbe stattfinden würde.***
Die Entsprechung der Figma die Mode-Schaltung: 
* Mutterkomponente beispielsweise "cole-tint-warm-white"
* Tochterkomponente hat ```<div data-theme="cole-tint-snow-white" class="bg-surface text-content p-lg font-primary">```


#++# 1. Die vier Schemata

| Element                | `cole-tint-surface-snow` | `cole-tint-surface-warm` | `purple-tint-surface-snow` | `purple-tint-surface-warm` |
| ---------------------- | ------------------------ | ------------------------ | -------------------------- | -------------------------- |
| Fläche                 | snow-white               | warm-white               | snow-white                 | warm-white                 |
| Tinte (Buttons/Akzent) | cole-tint                | cole-tint                | **purple-tint-light**      | **purple-tint-light**      |
| Input & Fließtext      | cole-tint                | cole-tint                | **purple-tint-dark**       | **purple-tint-dark**       |

**Regeln (wichtig):**
- **Ausgestanzte Labels** (Label auf gefülltem Button, selektiertes Label) = die **Surface-Farbe** (snow- bzw. warm-white je Modus).
-- Default-Modus für Sections: `cole-tint-surface-warm`.
-- Default-Modus für Card: `cole-tint-surface-snow`.
-- Default-Modus für Nav & Footer: `cole-tint-surface-snow`.

**Rollen-Regel (wichtig):**
- **Buttons, Segment, Toggle, laute Headline** nutzen im purple-Theme als Tinte `purple-tint-light`, aber **Inputs und Fließtext** nutzen im purple-Theme als Tinte `purple-tint-dark` (dunkler, lesbarer) - *nicht* dieselbe Tinte wie Buttons.
- **Icons** und **Buttons / IconButton** werden wie content behandelt und nutzen content-text

## 4. Tailwind / Dev-Handoff

Das Code-Äquivalent spiegelt Figma 1:1: **CSS-Variablen als semantische Tokens + Theme-Umschaltung per Container-Attribut** (`data-theme`). Ein Attribut oben, alles darunter erbt — identisch zum Figma-Modus-Pin.

### 4.1 Zwei Schichten (wie Figma)

```css
/* 1. Palette (= Clrs) */
:root {
  --cole-tint-90: #1d2020;
  --purple-tint-light-old: #57536f;
  --purple-tint-dark: #2a2740;
  --snow-white-100: #ffffff;
  --warm-white-100: #fff9f2;
}

/* 2. Semantik pro Theme (= Color Themes, 4 Modi) */
[data-theme="cole-snow"] {
  --surface: var(--snow-white-100);
  --button-primary-bg-default: var(--cole-tint-90);
  --button-primary-label-default: var(--snow-white-100); /* ausgestanzt = Surface */
  --content-text: var(--cole-tint-90);
  --input-text: var(--cole-tint-90);
}
[data-theme="purple-snow"] {
  --surface: var(--snow-white-100);
  --button-primary-bg-default: var(--purple-tint-light-old); /* Button = light */
  --button-primary-label-default: var(--snow-white-100);
  --content-text: var(--purple-tint-dark);                   /* Text = dark */
  --input-text: var(--purple-tint-dark);
}
/* cole-warm, purple-warm analog (warm-white statt snow-white) */
```

### 4.2 Tailwind-Config

```js
// tailwind.config.js — semantische Farben zeigen auf die Variablen (v3)
colors: {
  surface: 'var(--surface)',
  'button-primary': {
    bg: 'var(--button-primary-bg-default)',
    label: 'var(--button-primary-label-default)',
  },
  'content-text': 'var(--content-text)',
  'input-text': 'var(--input-text)',
}
// Tailwind v4: dasselbe Prinzip via @theme-Directive + CSS-Vars (native CSS)
```

### 4.3 Nutzung

```html
<section data-theme="purple-snow" class="bg-surface">
  <p class="text-content-text">Fließtext …</p>
  <button class="bg-button-primary-bg text-button-primary-label">Call to action</button>
</section>
```

### 4.4 Die drei Regeln (spiegeln Figma)

1. **Nie Palette-Werte im Component** — kein `bg-[#1d2020]` / `bg-cole-tint-90`, immer das semantische Utility (`bg-button-primary-bg`).
2. **Theme wird am Container gesetzt** (`data-theme`), nicht pro Komponente — der eine Schalter kaskadiert.
3. **Rollen-Logik steckt in den Token-Werten**, nicht im Component-Code — Input=dark, Button=light unterscheidet sich nur in den CSS-Variablen; der Component-Code ist für alle 4 Themes identisch.

## 5. Punktuelles Überschreiben (einzelne Komponente)

Vererbung ist „tieferer gewinnt" — ein einzelner Knoten darf den geerbten Modus für sich (und seinen Teilbaum) überschreiben.

- **Figma:** Instanz auswählen → im Appearance-Panel den `Clrs / Color Modes`-Modus explizit setzen. Überschreibt den Section-Modus nur für diese Instanz.
- **Code:** eigenes `data-theme` auf den Wrapper *dieser* Komponente setzen — die näher liegende CSS-Variablen-Definition gewinnt.

```html
<section data-theme="cole-snow" class="bg-surface">
  <p class="text-content-text">Standard-Theme der Section …</p>
  <div data-theme="purple-snow">
    <button class="bg-button-primary-bg text-button-primary-label">Sonder-CTA</button>
  </div>
</section>
```

Der Override gilt für den **ganzen Teilbaum** des Knotens. Soll nur der Button abweichen (nicht der Text daneben), muss der Wrapper eng um den Button sitzen. Auch hier gilt: die Komponente muss semantische Tokens binden, sonst greift weder Section-Modus noch lokaler Override.

## 6. Anderes
* **Wozu die Trennung zwischen box-spacing-[] Variablen und gap-[] Variablen?**
  Die Trennung erlaubt leichte Anpassung auf Click, auf kleinen Screens kann man gut am Rahmen sparen, während Gaps (vor allem vertikale Gaps, und auf kleinen Screens werden alle Gaps zu vertikalen Gaps) separat davon nicht wegrationalisiert werden können.

* **Welche Funktion erfüllen gebundene max-w-Variablen und min-w-Variablen?
   Der Wert der max-w Variablen könnte auf sehr großen Screens wachsen (durch zentrale Anpassung), ohne dass jede einzelne Componente Breakpoints braucht bzw. ohne die min-w Werte zu beeinträchtigen.
   Das selbe gilt umgekehrt für sehr kleine Screens (grob unter 400 px) 

## 7. Tooling
Die Figma-Variablen-Namen sind dev-freundlich (`button-primary-bg-default`). Mit **Tokens Studio** oder der **Figma Variables REST API** + **Style Dictionary** lässt sich das CSS-Variablen-Set direkt aus Figma generieren, statt es von Hand zu pflegen. Der `theme-name`-String liefert den passenden `data-theme`-Wert.

## Content-Struktur 
### Kategorien vs. Sammlungen
#### Feste Kategorien (Navigation)
- Bilden die Hauptnavigation und die Sitemap-Baumstruktur.
- Jedes Produkt gehört zu **genau einer** festen Kategorie – exklusiv!
- Beispiele: Nüsse, Trockenfrüchte, Saaten & Superfoods, Feinkost, Müsli & Backen, Snacks.

#### Sammlungen (thematische Produktgruppen)
- Zusätzliche, thematische Zusammenstellungen quer durch mehrere feste Kategorien.
- Ein Produkt kann in **mehreren** Sammlungen gleichzeitig auftauchen – nicht exklusiv.
- Eigene URLs/Kollektionsseiten, aber **nicht** Teil des Kategorie-Baums.
- Beispiele: "Alles fürs Radfahren", "Alles mit Schokolade", "Alles zum Selbstbacken", "Im Pfandglas", "Neu", "Voll beliebt", "Im Angebot" (noch zu verifizieren).
- Ob und wie Sammlungen in der Hauptnavigation angezeigt werden, wird später besprochen und ggf. implementiert._

## Komponenten-Hierarchie (Nomenklatur)

Festgelegt 21.07.2026. Vier Ebenen, von atomar nach komponiert:

1. **Primitives** — atomare Elemente, nicht allein einsetzbar (z. B. TableElement, Headlines, Paragraphs, ValidationSign, Icons).
2. **Content Modules** (Figma-Präfix: `ContentModules /`) — aus Primitives komponierte Content-Bausteine, die Content-Mitarbeiter:innen in Slots einsetzen (z. B. Ingredients, Basic, CTA, ContactForm).
3. **Components** — funktionale Verbünde (z. B. TabContent, TabControl, Checkout-Komponenten).
4. **Sections** — ganze Seitenabschnitte (z. B. Tabs, CustomSection, ReviewCards).

Der frühere Sammelbegriff „Patterns“ entfällt: atomare Patterns wurden zu Primitives umbenannt (Node-IDs unverändert), TextAndImg und Ingredients zu Content Modules (Figma-Präfix ohne Leerzeichen). Ältere „Patterns/…“-Erwähnungen in den Update-Notizen unten sind Historie.

**Neu 22.07.2026:** Kategorie `CMS /` — CustomContentWithImg und MediaText wurden von `ContentModules /` dorthin verschoben (eigene Figma-Section „CMS"); Einordnung in die Vier-Ebenen-Hierarchie folgt.

**Slot + Varianten kombiniert (Entscheidung 22.07.2026):** Sections und Content Modules mit austauschbarem Inhalt führen beides: einen **Slot** (mit Preferred Values, für den direkten Tausch) UND **pro erlaubtem Modul eine Variante**. Grund: Dev Mode und Component Playground zeigen Slot-Preferred-Values nicht an, wenn sie nicht zusätzlich als Varianten abgebildet sind und mit einer Property korrelieren — erst dann ist für Entwickler:innen sichtbar, welche Module eine Komponente aufnehmen kann. Beispiele: `Section / CustomSection` (SlotContent = CustomContentWithImg | MediaText), `CMS / CustomContentWithImg` (SlotContent = Basic | CTA | ContactForm | Ingredients, Slot „Content"). Slot-Defaults sind Instanzen von Content Modules, keine losen Primitives.

## Design Tokens: Null-Werte binden

**Auch `0` wird gebunden — nicht als nackte 0 belassen:** Gap = 0 bevorzugt an `gap-zero`, Padding = 0 an `box-spacing-zero` (beide aliasen `[twuc]-0 (0rem)`). So ist auch „bewusst kein Abstand" explizit als Design-Entscheidung sichtbar.

**Wirkungslose Gaps** werden auf 0 gesetzt und an `gap-zero` gebunden: Ein `itemSpacing` wirkt nur zwischen ≥ 2 Kindern — ist ein Auto-Layout-Frame mit weniger als 2 Kindern (ausgeblendete Elemente mitgezählt, da sie sichtbar werden könnten), ist der Gap tot. `counterAxisSpacing` auf Frames ohne `layoutWrap: WRAP` bleibt unangetastet (latente Property, kein sichtbarer Gap — kein Rauschen erzeugen).

## Design Tokens: Breiten & Höhen (min/max)

Für **min-/max-Breiten und -Höhen von Komponenten** bevorzugt Variablen aus diesen beiden Collections binden statt fester Pixelwerte:

- **`Lyt scl / Width`** — min-w/max-w je Komponententyp (z. B. `Cards/Default/min-w`, `Buttons/max-w`, `Block Element/Large/min-w`, `Mega Cards/max-w`).
- **`Lyt scl / Heights`** — fix-h/min-h/max-h (z. B. `btns/Large/fix-h`, `Cards/Mid/max-h`, `Input/Search/fix-h`).

Nur wenn kein passender Wert existiert, auf die Tailwind-Utility-Skala (`Lyt scl / Tailwind-utility-units`, `[twuc]-N`) zurückgreifen. Feste Pixelwerte in Mastern vermeiden.

**Bei Unklarheit die Nutzerin fragen:** Ist nicht eindeutig, welche min-w/max-w- oder Höhen-Gruppe für eine Komponente passt, nachfragen — oder ob ein neuer Wert in `Lyt scl / Width` bzw. `Lyt scl / Heights` hinterlegt werden soll. Nicht raten.

## Buttons: Hug / Fill / Fixed-Verhalten
- Figma übersetzt Hug/Fill-Einstellungen unter bestimmten Bedingungen in absolute Fixed-Werte. Das ist nicht so gedacht – Ausnahmen sind Min/Max-Constraints und (absolut selten) bewusst gesetzte Fixwerte. In 99% der Fälle sind Fixwerte mit einer Variable verknüpft, nicht hart kodiert. Immer die Properties Fixed / Fill / Hug prüfen statt absolute Werte zu übernehmen.
- Das Hintergrund-SVG passt sich grundsätzlich an das Mutter-Frame an.
- Buttons für Tarabao sind so gebaut, dass Hintergrund und Rahmen ein SVG sind.
- Sizing-Regeln Button / Label:
  - Button = Fill → Label = Fill + truncate.
  - Button = Fixed → Label = Fill.
  - Button = Hug → Label = Fill.
