# 2.6 Design Tokens: Implementierung in Tailwind v4 (`app.tcss`)

Konkrete Umsetzung der in [`2.3-tailwind-dev-handoff.md`](2.3-tailwind-dev-handoff.md) beschriebenen Architektur als **eine** CSS-Datei.
Ergänzt den Dev-Handoff um: Namespace-Regeln von Tailwind v4, die vollständigen Modus-Blöcke,
die Verifikation und die Namenskonventionen Figma → CSS. Die drei Regeln für Komponenten stehen im Dev-Handoff §6.

Build geprüft mit Tailwind v4.3.3.

---

## 1. Quellen: welche Collections wandern wohin

Ausgeschlossen sind **ausschließlich** Collections mit `__`-Präfix (Inhalts-/Textdaten,
nicht Design-Tokens). Alle übrigen sind abgebildet.

| Figma-Collection | Ziel im CSS |
|---|---|
| `Clrs / Primitives` | `:root` — Rohpalette, **nie** direkt in Komponenten |
| `Clrs / Color Modes` | `@theme inline` + 4 × `[data-theme]` |
| `Clrs / Filter Panel` | `:root` (single-mode) |
| `Clrs / Search` | `:root` (single-mode) |
| `Clrs / Sustainability Tags` | `:root` (single-mode) |
| `Clrs / NutmixerTags` | `:root` (single-mode) |
| `Clrs / Mega Cards` | `[data-lively-theme]` (4 Modi) |
| `Clrs / Special` | `[data-special-theme]`, Präfix `--special-*` (2 Modi) |
| `Typografy` | `--text-*` |
| Text Styles | `--font-*` (Familien), `--leading-*`, `--tracking-*`; je Stil eine Klasse `@utility type-*` (§6a) |
| `Lyt scl / Spcngs / Box Spacing` | `--spacing-*` |
| `Lyt scl / Spcngs / Gaps` | `--spacing-*` (dieselbe Skala, s. §5) |
| `Lyt scl / Tailwind-utility-units` | Basis-rem-Skala hinter Box/Gaps |
| `Lyt scl / Breakpoints` | `--breakpoint-md`, `--breakpoint-lg`; `--breakpoint-*: initial` entfernt die Tailwind-Standards `sm`, `xl`, `2xl`. Nur Figma: `base`, `calc(md - 1)`, `calc(lg - 1)` |
| `Lyt scl / Width` | `--container-*` (Namen = Code-Syntax der Variablen); Werte je Modus setzt `:root` ab md/lg neu. `min-w-content` / `max-w-content` → `--content-min` / `--content-max` mit eigener `@utility` (§6). Nur Figma: `viewport-range`, `min-w-screen`, `max-w-screen`, `visible-md-up` |
| `Lyt scl / Heights` | `@utility` (s. §3) |

## 2. Namespaces: die drei Fallen von Tailwind v4

In v4 erzeugt ein Theme-Token nur dann Utilities, wenn es im **richtigen** Namespace steht.
Ein falscher Präfix wirft **keinen Fehler** — die Tokens sind einfach stumm. Drei typische Fälle:

| Zweck | ❌ falsch | ✅ richtig | erzeugt |
|---|---|---|---|
| Schriftgröße | `--font-size-16` | `--text-16` | `text-16` |
| Breite | `--width-btn-max` | `--container-btn-max` | `w-`, `min-w-`, `max-w-`, `basis-` |
| Höhe | `--height-btn-lg` | *kein Namespace* → `@utility` | `h-btn-lg` |

`--font-*` ist ausschließlich die **Schriftfamilie**, nicht die Größe. Für Höhen existiert
in v4 kein Theme-Namespace — die Werte bleiben normale Custom Properties und werden per
`@utility` freigegeben.

**Merksatz:** Nach jeder Token-Änderung einmal bauen und im Output prüfen, ob die Klasse
wirklich existiert. Stumme Tokens fallen sonst erst im Layout auf.

## 3. Aufbau der Datei

```
1. Primitives            :root                      Rohwerte
2a. Color Modes          :root + 4 × [data-theme]   global themebar
2b. Single-Mode          :root                      Filter Panel, Search, Sustainability Tags, NutmixerTags
2c. Lively Themes        :root + [data-lively-theme] Mega Cards (Karte + LG-Buttons)
2d. Heights              :root                      Basis für @utility
2e. Special              :root + [data-special-theme] Voucher, PromoBar
3. @theme inline         Farben → Utilities         laufzeit-umschaltbar
4. @theme static         Text, Spacing, Container   statisch, alle Variablen ausgegeben
   :root + @variant      Breiten je Breitenbereich  --container-*, --content-*
5. @utility              Höhen, min-w-content, max-w-content
6. @utility type-*       Textstile                  eine Klasse je Figma-Textstil
```

**Kein `*/` in Kommentaren.** Die Zeichenfolge beendet einen CSS-Kommentar sofort, auch
mitten in `Buttons/*/Inline`. Der Rest des Kommentars wird dann zum Selektor des nächsten
Blocks, und der Browser verwirft diesen Block. Pfad-Platzhalter deshalb als `Buttons/…/Inline` schreiben;
`token-check` meldet solche Fälle als `SELEKTOR`.

`@theme inline` ist bei den Farben **Pflicht**: nur so geben die Utilities `var(--…)` aus und
bleiben zur Laufzeit über `data-theme` umschaltbar. Ohne `inline` friert v4 die Werte beim
Build ein. Die statischen Skalen (Text, Spacing, Container, Breakpoints) stehen in
`@theme static`: v4 gibt dann jede Variable aus, auch wenn keine Utility sie nutzt. Normales
`@theme` wirft ungenutzte Variablen weg, dann liefe `var(--spacing-lg)` aus Dev Mode ins Leere.

## 4. Die 4 Modi — Blöcke müssen VOLLSTÄNDIG sein

Die vier Figma-Modi werden zu vier `data-theme`-Werten:

```
cole-tint-surface-warm    (Default)
cole-tint-surface-snow
purple-tint-surface-warm
purple-tint-surface-snow
```

**Regel: jeder Block deklariert alle Tokens der Collection — keine Diffs.**

Keine Stilfrage, sondern Voraussetzung für das lokale Überschreiben aus dem [Dev-Handoff §3](2.3-tailwind-dev-handoff.md).
Custom Properties **erben**. Ein Block, der nur die Abweichungen gegenüber dem Default setzt,
funktioniert nur, solange sein Elternknoten der Default ist. Sobald verschachtelt wird, erbt
er für jedes nicht erneut gesetzte Token die Werte des Elternmodus:

```html
<!-- mit Diff-Blöcken defekt: Card erbt purple-Textfarben auf snow-Fläche -->
<section data-theme="purple-tint-surface-warm">
  <article data-theme="cole-tint-surface-snow">…</article>
</section>
```

Zweiter Punkt: der Default braucht einen **eigenen Selektor**. Steht er nur auf `:root`, kann
kein Teilbaum zurück auf `cole-tint-surface-warm` geschaltet werden:

```css
:root,
[data-theme="cole-tint-surface-warm"] { /* … alle Tokens … */ }
```

Gleiches gilt für die `data-lively-theme`-Achse (Default `blue-pistacio-green`).

> Die Redundanz ist gewollt. Vier vollständige Blöcke sind der Preis dafür, dass Verschachtelung sich
> genau wie ein Figma-Modus-Pin verhält.

## 5. Spacing: eine Skala statt Box-Spacing und Gaps

In Tailwind lesen `p-*`, `m-*`, `gap-*` und `space-*` **alle** aus demselben `--spacing-*`.
Da Box Spacing und Gaps in Figma pro Stufe identische Werte haben, werden sie im Code zu
einer Skala zusammengeführt — das ist die übliche Lösung, keine Vereinfachung.

| Token | rem | px | Figma |
|---|---|---|---|
| `--spacing-zero` | 0 | 0 | `box-spacing-zero` / `gap-zero` |
| `--spacing-xxxs` | 0,125rem | 2 | `…-xxxs` |
| `--spacing-xxs` | 0,25rem | 4 | `…-xxs` |
| `--spacing-xs` | 0,375rem | 6 | `…-xs` |
| `--spacing-sm` | 0,5rem | 8 | `…-sm` |
| `--spacing-md-sm` | 0,75rem | 12 | `…-md-sm` |
| `--spacing-md` | 1rem | 16 | `…-md` |
| `--spacing-md-l` | 1,25rem | 20 | `…-md-l` |
| `--spacing-lg` | 1,75rem | 28 | `…-lg` |
| `--spacing-xl` | 2,5rem | 40 | `…-xl` |
| `--spacing-xxl` | 3rem | 48 | `…-xxl` |
| `--spacing-xxxl` | 3,5rem | 56 | `…-xxxl` |

`p-md` und `gap-md` ergeben also beide 1rem. Im Code hat die Trennung in zwei Figma-Collections
kein Gegenstück.

**Wozu die Trennung zwischen box-spacing-[] Variablen und gap-[] Variablen?**
Die Trennung erlaubt leichte Anpassung auf Click, auf kleinen Screens kann man gut am Rahmen sparen, während Gaps (vor allem vertikale Gaps, und auf kleinen Screens werden alle Gaps zu vertikalen Gaps) separat davon nicht wegrationalisiert werden können. Außerdem filtert sie in Figma den Variablen-Picker auf Padding bzw. Gap.

**Achtung:** v4s dynamische Zahlenskala bleibt aktiv, `p-4` funktioniert weiter und umgeht
die Tokens. Wer das unterbinden will, setzt vor der Skala `--spacing-*: initial;`.

## 5a Leading & Tracking: relative Skalen direkt auf den Text Styles

Zeilenhöhe (Leading) und Zeichenabstand (Tracking) liegen **nicht** als Figma-Variablen vor,
sondern als Prozentwerte direkt auf den Text Styles. Grund: **Figma erlaubt (noch) keine
Prozentwerte als Variablen** — Number-Variablen sind einheitenlose Zahlen und gelten an
`lineHeight` / `letterSpacing` als Pixel. Eine relative %-Skala (Minimum = Fonthöhe, skaliert
mit jeder Größe) ist als Variable daher nicht ablegbar; zu Pixeln fixiert würde sie zudem
nicht zur rem-basierten Ausgabe passen.

**Leading (relativ %):**

| Token | Wert | Verwendung |
|---|---|---|
| `--leading-tighter` | 85 % → `0.85` | Ausnahme: H1 Subtitle (Display, bewusst unter Fonthöhe) |
| `--leading-tight` | 100 % → `1` | einzeilig: Buttons, Labels, Inputs, Nav, Tabellen-Header |
| `--leading-heading` | 115 % → `1.15` | umbrechende Titel/Headlines |
| `--leading-body` | 140 % → `1.4` | Fließtext mit Umbruch |
| `--leading-relaxed` | 160 % → `1.6` | längere Lesetexte (Reserve) |

**Tracking (relativ %):**

| Token | Wert | Verwendung |
|---|---|---|
| `--tracking-tight` | −2 % → `-0.02em` | Display-Fonts (LUMOSKY, BROWN NOW) |
| `--tracking-normal` | 0 % → `0em` | Fließtext & UI (Manrope) |
| `--tracking-wide` | +2 % → `0.02em` | kleine gesperrte Labels (Navigation/Route) |

**Figma → CSS:** Figma-% ÷ 100. `line-height` **einheitenlos** (multipliziert die eigene
Schriftgröße, skaliert mit rem), `letter-spacing` in **em** (skaliert mit der Größe, `px` nicht).
Im `app.tcss` liegen sie im statischen `@theme` (Namespaces `--leading-*` → `leading-*`,
`--tracking-*` → `tracking-*`).

Anders als eine Variable ist die Skala damit nicht an einer Stelle zentral editierbar — eine
Änderung heißt, die betroffenen Text Styles anzupassen. Welche Stufe ein Stil nutzt, steht in
seiner Klasse `type-*` (§6a).

## 6. Breiten & Höhen

Breiten laufen über `--container-*`. Der Token-Name steht in Figma als **Code syntax → Web** an jeder Width-Variable (z. B. `Block Element/min-w` → `var(--container-block-min)`). Die Klasse ist Präfix plus Token-Name ohne `--container-`: `min-w-block-min`. Namensregel: `<komponente>-<größe>-min` bzw. `-max`, klein; `DefaultSize` entfällt, `Buttons` → `btn`, `Cards` → `card`.

Werte, die sich je Breitenbereich ändern, stehen mit dem base-Wert in `@theme`. Ein `:root`-Block setzt sie mit `@variant md` / `@variant lg` neu. Das entspricht dem Modus an der Figma-Section, in der die Seiten liegen. So braucht die Komponente nur eine Klasse. Details: [2.5](2.5-breakpoints-und-width.md).

`min-w-content` und `max-w-content` tragen als Klassen genau die Figma-Namen. Sie stehen deshalb
nicht im Namespace `--container-*`, sondern als `--content-min` / `--content-max` in `:root` und
mit eigener `@utility`. Ein Token `--container-content` erzeugte neben `max-w-content` auch
`min-w-content` mit dem Maximalwert. Breiten, die in Figma auf `max-w-content` verweisen
(`Mega Cards/max-w`, `Block Element/Double/max-w`, `Panel/max-w`), verweisen im CSS auf
`var(--content-max)` und schalten damit automatisch mit.

Höhen brauchen `@utility`:

```css
@utility h-btn-lg { height: var(--height-btn-lg); }
@utility min-h-card-md { min-height: var(--height-card-md-min); }
```

## 6a. Textstile als Klassen

Jeder Figma-Textstil ist in §6 von `app.tcss` eine Klasse `type-*`. Sie setzt Familie, Größe,
Gewicht, Zeilenhöhe, Laufweite und, falls vorhanden, Großschreibung, Unterstreichung und den
Absatzabstand. Alle Werte verweisen auf die Tokens aus §4 (`--font-*`, `--text-*`,
`--leading-*`, `--tracking-*`, `--spacing-*`).

Der Klassenname folgt mechanisch aus dem Stilnamen: Präfix `type-`, `/` und Leerzeichen werden
`-`, Binnenmajuskeln werden getrennt, `&` und `<>` entfallen, alles klein.

| Figma-Textstil | Klasse |
|---|---|
| `H1` | `type-h1` |
| `Navigation/Route` | `type-navigation-route` |
| `ShoppingCart & Checkout/MainHeadline` | `type-shopping-cart-checkout-main-headline` |
| `Table/<th>` | `type-table-th` |
| `DefaultText LG` | `type-default-text-lg` |

Der Absatzabstand aus Figma wirkt zwischen zwei Absätzen desselben Stils (`& + &`).
`token_check.py --emit-type` erzeugt den Block aus dem Figma-Dump neu.

## 7. Verifikation

Zwei Schritte, beide bei jeder Änderung:

1. **Bauen:** `npx @tailwindcss/cli -i app.tcss -o out.css` und im Output prüfen, ob die
   erwarteten Klassen existieren. Falsche Namespaces sind stumm (§2).
2. **Abgleich mit Figma:** `2-tarabao/token-check/figma-dump.js` in `use_figma` ausführen,
   die Ausgabe als `dump.txt` speichern, dann
   `python3 2-tarabao/token-check/token_check.py dump.txt 2-tarabao/app.tcss`.
   Das Skript prüft jede Code-Syntax `var(--x)` gegen `app.tcss`, löst jeden Wert je Modus bis
   zum Endwert auf, zählt die Theme-Blöcke auf Vollständigkeit, prüft die Farb-Utilities und
   vergleicht jeden Textstil mit seiner Klasse `type-*`. Ziel: 0 Fehler.

Die vollständigen Prüfschritte stehen in der Skill-Datei `1-figma-claude-technical/1.7-tarabao-token-sync-skill.md`.

## 9. Namenskonventionen (Figma → CSS eindeutig halten)

Ziel: die Übertragung ist ableitbar, nicht auslegungsbedürftig.

### 9.1 Zustands-Vokabular (geschlossen)

| Suffix | Bedeutung |
|---|---|
| `-default` | Ruhezustand |
| `-hover` | Hover |
| `-focused` | Feld hat den Fokus, wird benutzt (Inputs, Search) |
| `-selected` | ausgewählt |
| `-selected-hover` | ausgewählt **und** Hover |
| `-inactive` | löst keine Aktion aus |
| `-hover-&-click` | ein Token deckt Hover **und** Klick ab |

Zustände tragen kein Präfix `on-`. Deckt **ein** Token zwei Zustände ab, gilt die
`&`-Schreibweise in fester Reihenfolge: `-hover-&-click`.

**`-inactive`, nicht `-disabled`:** der Button bleibt klickbar und gibt eine Fehlermeldung
zurück — er ist also nicht technisch deaktiviert. `-disabled` würde das Verhalten falsch
beschreiben; es wird nur verwendet, wenn wirklich das HTML-Attribut gemeint ist.

**`-focused`, nicht `-active`:** ein Feld in Benutzung entspricht `:focus`. In CSS bedeutet
`:active` dagegen „wird gerade gedrückt" — für Inputs also der falsche Begriff. Deshalb kommt
`-active` als eigenständiges Suffix nicht vor; gedrückte Zustände stecken in
`-hover-&-click`.

### 9.2 Property-Vokabular

`bg`, `label`, `stroke` — kombinierte Tokens immer in der Reihenfolge `label-&-stroke`
(nicht `stroke-&-label`). Das `&` heißt: **eine** Variable versorgt zwei CSS-Eigenschaften,
im Code also zwei Utilities aus einem Token.

### 9.3 Modus-Namen: genau eine Achse

Ein Modus-Name kodiert genau eine Dimension. MegaCard und ihre LG-Buttons liegen in **einer**
Collection (`Clrs / Mega Cards`). Die vier Modi sind die Kampagnen selbst:
`blue-pistacio-green`, `orange-black`, `happy-christmas`, `purple-black`.
Im CSS entsprechend `[data-lively-theme="orange-black"]` usw. — ohne Gruppen-Präfixe, weil
Karte und Button gemeinsam umschalten.

> **Konsequenz:** Karte und Button lassen sich nicht unabhängig thematisieren — ein Modus
> schaltet beides. „Christmas-Karte mit purple Button" wäre ein zusätzlicher Modus.

### 9.4 Schreibweise

Variablennamen kebab-case, keine Leerzeichen (`peachy-coral`).
Gruppennamen dürfen Leerzeichen behalten (`Price Range Filter`) — die Ableitung nutzt den Leaf.

**Keine Zahl im Namen, die dem Wert widersprechen kann.** Bei Abweichung gilt der
**px-Wert**, der Name wird korrigiert. Beispiel: `[twuc]-312 (78rem)` = 1248 px.

### 9.5 Ableitung Figma → CSS

**Code syntax → Web** trägt an jeder Figma-Variable den CSS-Namen aus `app.tcss`, z. B.
`box-spacing-xl (40px)` → `var(--spacing-xl)`, `Button-Primary/button-primary-bg-default` →
`var(--btn-primary-bg)`. Dev Mode zeigt diesen Namen statt des Figma-Namens. Farben zeigen auf
die Laufzeit-Variable (`--btn-primary-bg`), nicht auf `--color-*` aus `@theme inline`, da diese
nicht ausgegeben wird. `Lyt scl / Tailwind-utility-units` zeigt auf die Tailwind-Grundeinheit:
`[twuc]-5 (1,25rem)` → `calc(var(--spacing) * 5)`. Ohne Code-Syntax bleiben nur Figma-only-
Variablen (`viewport-range`, `min-w-screen`, `max-w-screen`, `visible-md-up`, `base`, `calc(md - 1)`,
`calc(lg - 1)`; Beschreibung „Nur Figma“). Neue Variable → Code-Syntax im selben Zug setzen.

`Gruppe/leaf-<rolle>-<zustand>` → `--<kurzform>-<rolle>-<zustand>`: `button` → `btn`,
`-default` entfällt, das Kategorie-Präfix bleibt erhalten (es verhindert Kollisionen,
nicht die Rolle). Der Leaf spiegelt seine Gruppe. Beispiel:
`OptionSelection/option-selection-button-bg-default` → `--btn-option-selection-bg`
(Utility `bg-btn-option-selection-bg`), gleiche Form wie `--btn-primary-*`. Sets auf einer
eigenen Achse behalten ihr Präfix (`--megacard-btn-primary-*`, `--megacard-btn-inline-*`).

Farbwerte stehen im CSS so, wie Figma sie hält. Korrekturen an Farbwerten passieren in Figma,
nicht im CSS.

**Achtung bei Umbenennungen:** ein Token-Name steht an drei Stellen — in allen vier
Modus-Blöcken, in der `@theme inline`-Registrierung und auf deren rechter Seite (`var(--…)`).
Wird nur ein Teil umgestellt, ist die Variable nur in manchen Modi definiert und die Utilities
fallen in den übrigen still aus — ohne Build-Fehler. Nach jeder Umbenennung prüfen: kommt der
alte Name nirgends mehr vor, und stimmen Registrierung und Referenz überein?

### 9.6 Gruppen-Ebenen

Genau **eine** Gruppen-Ebene pro Collection, damit jede Variable die Form `Gruppe/leaf` hat.
Eine zweite Ebene trägt keine Information, weil der Leaf die Gruppe schon spiegelt
(`OptionSelection/option-selection-button-…`).

Die Unterscheidung **standardisierte vs. spezialisierte Buttons** bleibt bewusst über die
Gruppennamen erhalten (`Button-Primary/-Secondary/-Inline` vs. `Segmented`, `Counter`,
`OptionSelection`). Ein einheitliches `Button-`-Präfix wäre für die Ableitung ohne Nutzen —
die greift auf den Leaf zu — und würde die Unterscheidung verwischen.

### 9.7 Breiten: Rolle statt Größenleiter

Die Gruppen in `Lyt scl / Width` sind nach **Rolle** benannt, nicht nach einer Größenleiter (Werte base · md · lg, sonst in allen Modi gleich):

| Gruppe | Variablen → Token | Werte (px) |
|---|---|---|
| Seitenrahmen | `max-w-content` → `--content-max`, `min-w-content` → `--content-min` (Klassen = Figma-Namen) | 768 · 1024 · 1248; 320 · 728 · 984 |
| Seitenrahmen, nur Figma | `viewport-range`, `min-w-screen`, `max-w-screen`, `visible-md-up` | ohne Token |
| `Block Element` | `min-w` → `block-min`, `max-w` → `block-max`, `Inline/min-w` → `block-inline-min`, `Double/max-w` → `block-double-max` | 320 · 320 · 384; 512; 96; → max-w-content |
| `Product Page` | `column-min-w` → `product-page-column-min` | 320 · 328 · 328 |
| `Cards/DefaultSize` | `min-w` → `card-min`, `max-w` → `card-max`, `Img/max-w` → `card-img-max` | 240; 384; 208 |
| `Cards/CompactSize` | `min-w` → `card-compact-min`, `max-w` → `card-compact-max`, `Img/max-w` → `card-compact-img-max` | 240; 328; 208 |
| `Cards/Small`, `Cards/Discovery` | `card-small-min`, `card-discovery-max` | 256; 672 |
| `Panel` | `min-w` → `panel-min`, `max-w` → `panel-max` | 320 · 384 · 384; → max-w-content |
| `Overlay Message` | `min-w` → `overlay-message-min`, `max-w` → `overlay-message-max` | 320 · 384 · 384; 512 |
| `Buttons` | `btn-min`, `btn-max`, `Payment/max-w` → `btn-payment-max` | 240; 512; 448 |
| `Nav/Block` | `nav-block-min`, `nav-block-max` | 112; 256 |
| `Fieldset`, `Footer` | `fieldset-min`, `footer-header-max` | 240; 448 |
| `Search`, `ImpactScale` | `search-max`, `impact-scale-min`, `impact-scale-max` | 600; 128; 224 |
| `List Item`, `Icons` | `list-item-img-min`, `icon-counter-min` | 72; 14 |
| `Mega Cards` | `megacard-min`, `megacard-max` | 320 · 424 · 424; → max-w-content |

`min-w-content` ist die Obergrenze für jedes min-w im Modus base (Fenster − 2 × 20 px Rand).

**Jede Variable hat eine Beschreibung**, die die konsumierenden Komponenten-Kategorien nennt.
Sie ist im Figma-Picker sichtbar.
