# 2.3 Tailwind v4 / Dev-Handoff (Markup)

Das Code-Äquivalent spiegelt Figma 1:1: **semantische Tokens als CSS-Variablen + Theme-Umschaltung per Container-Attribut** (`data-theme`). Ein Attribut oben, alles darunter erbt — identisch zum Figma-Modus-Pin. Tailwind v4 ist **CSS-first** (kein `tailwind.config.js` nötig): Tokens werden per `@theme` definiert und daraus die Utilities generiert. Alle Tokens stehen in [`app.tcss`](app.tcss), die Architektur erklärt [2.6 Design-Tokens](2.6-design-tokens-tailwind-v4.md).

Klassen stehen immer in zwei Schreibweisen: zuerst die Klasse aus unserem Designsystem (`app.tcss`), dahinter in Klammern die Tailwind-Standardklasse.

## 1 Aufbau (zwei Schichten wie Figma)

```css
@import "tailwindcss";

/* 1) Palette (= Clrs / Primitives) — Rohwerte, nie direkt in der Komponente nutzen */
:root {
  --cole-tint-90: #1d2020e5;
  --purple-tint-light-old: #57536f;
  --purple-tint-dark-dark: #25232b;
  /* … restliche Palette … */
}

/* 2) Semantische Utilities (= Clrs / Color Modes).

      `inline` ist wichtig: so geben die Utilities `var(--…)` aus und
      bleiben zur Laufzeit über data-theme umschaltbar. */
@theme inline {
  --color-surface: var(--surface-color);
  --color-content-text: var(--content-text);
  --color-btn-primary-bg: var(--btn-primary-bg);
  --color-btn-primary-label: var(--btn-primary-label);
  --color-segmented-bg-selected: var(--segmented-bg-selected);
  /* … alle Color-Themes-Tokens … */
}
```

**Merke:** Ein `--color-<name>`-Token erzeugt in v4 automatisch **alle** Farb-Utilities dieses Namens. Beispiel für `--color-btn-primary-bg` — jedes Utility setzt eine andere CSS-Eigenschaft auf denselben Token-Wert:

| Utility                           | CSS-Eigenschaft                 | typische Nutzung im DS                       |
| --------------------------------- | ------------------------------- | -------------------------------------------- |
| `bg-btn-primary-bg`            | `background-color`              | Flächen (Button-BG, Surface, Card)           |
| `text-btn-primary-bg`          | `color`                         | Text **und** Icons, die `currentColor` erben |
| `border-btn-primary-bg`        | `border-color`                  | Rahmen / Stroke                              |
| `fill-btn-primary-bg`          | `fill`                          | SVG-Icons (gefüllt)                          |
| `stroke-btn-primary-bg`        | `stroke`                        | SVG-Icons (Kontur)                           |
| `ring-btn-primary-bg`          | Ring-Farbe (`--tw-ring-color`)  | Focus-Ring                                   |
| `outline-btn-primary-bg`       | `outline-color`                 | Focus-Outline                                |
| `divide-btn-primary-bg`        | `border-color` zwischen Kindern | Trennlinien in Listen                        |
| `decoration-btn-primary-bg`    | `text-decoration-color`         | Unterstreichungen                            |
| `accent-btn-primary-bg`        | `accent-color`                  | Checkbox/Radio/Range                         |
| `caret-btn-primary-bg`         | `caret-color`                   | Text-Cursor in Inputs                        |
| `from-/via-/to-btn-primary-bg` | Gradient-Stops                  | Farbverläufe                                 |

Aus `var(--x)` im Dev Mode wird `bg-x`, `text-x`, `border-x` usw. Einzige Ausnahme: `var(--surface-color)` → `bg-surface`.

Ohne `inline` würde v4 den Wert beim Build „einfrieren" — dann funktioniert die Laufzeit-Umschaltung (`data-theme`) nicht.

Zwei `@theme`-Blöcke: **Farben** in `@theme inline` (bleiben zur Laufzeit umschaltbar),
**statische Skalen** in `@theme static` — `--text-*` (Schriftgrößen), `--leading-*` (Zeilenhöhe), `--tracking-*` (Zeichenabstand), `--spacing-*`
(Padding und Gap aus einer Skala), `--container-*` (Breiten). `static` gibt jede Variable aus, auch wenn keine Utility sie nutzt.
Deshalb funktioniert `var(--spacing-lg)` aus dem Dev Mode auch in handgeschriebenem CSS. Höhen haben in v4
**keinen** Theme-Namespace und laufen über `@utility` (`h-btn-lg` …).

## 1.1 Leading & Tracking (Typografie-Skalen)

Zeilenhöhe und Zeichenabstand kommen als relative %-Skalen (in Figma direkt auf den Text
Styles, nicht als Variablen — Figma erlaubt noch keine %-Variablen). Im Code:

| Klasse | CSS | Wert / Verwendung |
|---|---|---|
| `leading-tighter` | `line-height: 0.85` | 85 % — H1 Subtitle (Display, tight) |
| `leading-tight` | `line-height: 1` | 100 % — einzeilig (Buttons, Labels, Inputs, Nav) |
| `leading-heading` | `line-height: 1.15` | 115 % — umbrechende Titel |
| `leading-body` | `line-height: 1.4` | 140 % — Fließtext |
| `leading-relaxed` | `line-height: 1.6` | 160 % — lange Lesetexte |
| `tracking-tight` | `letter-spacing: -0.02em` | −2 % — Display (LUMOSKY, BROWN NOW) |
| `tracking-normal` | `letter-spacing: 0em` | 0 % — Fließtext & UI (Manrope) |
| `tracking-wide` | `letter-spacing: 0.02em` | +2 % — kleine gesperrte Labels |

`line-height` ist einheitenlos (skaliert mit der rem-Schriftgröße), `letter-spacing` in `em`.

```html
<h2 class="text-32 leading-heading tracking-tight">Titel, der umbrechen darf</h2>
<p class="text-16 leading-body tracking-normal">Fließtext …</p>
```

## 1.2 Textstile: eine Klasse je Figma-Textstil

Für jeden Textstil aus Figma gibt es eine fertige Klasse `type-*`. Sie setzt Familie, Größe,
Gewicht, Zeilenhöhe, Laufweite und, wo Figma es vorgibt, Großschreibung, Unterstreichung und
den Absatzabstand. Der Dev Mode zeigt den Stilnamen, daraus ergibt sich die Klasse:
Präfix `type-`, `/` und Leerzeichen werden `-`, Binnenmajuskeln werden getrennt, `&` und `<>`
entfallen, alles klein.

| Figma-Textstil | Klasse |
|---|---|
| `H1` | `type-h1` |
| `Buttons/LG Underlined` | `type-buttons-lg-underlined` |
| `ShoppingCart & Checkout/MainHeadline` | `type-shopping-cart-checkout-main-headline` |
| `Table/<th>` | `type-table-th` |
| `DefaultText LG` | `type-default-text-lg` |

```html
<h1 class="type-h1 text-content-loud-headline">Unsere Nüsse</h1>
<p class="type-default-text-lg">Erster Absatz …</p>
<p class="type-default-text-lg">Zweiter Absatz, mit dem Absatzabstand aus Figma darüber.</p>
```

Die Farbe gehört nicht zum Textstil, sie kommt wie bisher aus dem semantischen Utility.
Die Einzelklassen aus §1.1 bleiben für Fälle ohne Textstil. Alle Stile mit ihren Werten stehen in `app.tcss` §6.

## 1.3 Breakpoints und Inhaltsbreite

Es gibt nur die Varianten `md:` (ab 768 px) und `lg:` (ab 1024 px), dazu `max-md:` und
`max-lg:`. Die Tailwind-Standards `sm:`, `xl:` und `2xl:` sind abgeschaltet, da es sie in Figma
nicht gibt.

`max-w-content` und `min-w-content` heißen genau wie die Figma-Variablen und passen ihren Wert
selbst an den Breitenbereich an (max 768 · 1024 · 1248 px, min 320 · 728 · 984 px). Ab 1248 px
Fensterbreite bleibt der Inhalt stehen und wird zentriert:

```html
<section class="bg-surface">
  <div class="mx-auto max-w-content px-md-l">…</div>   <!-- Figma-Ebene „Wrapper [max-w-content]“ -->
  <!-- (max-w-192 md:max-w-256 lg:max-w-312 px-5, wenn das Designsystem nicht vollständig aktualisiert worden sein sollte) -->
</section>
```

Details: [2.5](2.5-breakpoints-und-width.md).

## 2 Die 4 Modi (globales Theme)

Die vier Figma-Modi = vier `data-theme`-Werte. Pro Theme werden nur die **semantischen** Variablen neu gesetzt (nicht die Palette, nicht die `--color-*`). Auszug aus `app.tcss`:

```css
:root,
[data-theme="cole-tint-surface-warm"] {
  --surface-color: var(--warm-white-100);
  --content-text: var(--cole-tint-100);
  --btn-primary-bg: var(--cole-tint-90);
  --btn-primary-label: var(--warm-white-80);   /* ausgestanzt = Surface */
}
[data-theme="cole-tint-surface-snow"] {
  --surface-color: var(--snow-white-100);
  --content-text: var(--cole-tint-100);
  --btn-primary-bg: var(--cole-tint-90);
  --btn-primary-label: var(--warm-white-80);
}
[data-theme="purple-tint-surface-warm"] {
  --surface-color: var(--warm-white-100);
  --content-text: var(--purple-tint-dark-dark);   /* Fließtext = dark */
  --btn-primary-bg: var(--purple-tint-light-old); /* Button = light */
  --btn-primary-label: var(--warm-white-80);
}
[data-theme="purple-tint-surface-snow"] {
  --surface-color: var(--snow-white-100);
  --content-text: var(--purple-tint-dark-dark);
  --btn-primary-bg: var(--purple-tint-light-old);
  --btn-primary-label: var(--snow-white-90);
}
```

Jeder Block setzt in `app.tcss` alle Tokens der Collection, nicht nur diese vier. Warum: [2.6 Design-Tokens §4](2.6-design-tokens-tailwind-v4.md).

### 2.1 Nutzung

```html
<section data-theme="purple-tint-surface-snow" class="bg-surface">
  <p class="text-content-text">Fließtext …</p>
  <button class="bg-btn-primary-bg text-btn-primary-label">Call to action</button>
</section>
```

## 3 Punktuelles Überschreiben (tieferer gewinnt)

Ein eigenes `data-theme` auf einem Wrapper überschreibt den geerbten Modus für dessen ganzen Teilbaum — identisch zum lokalen Figma-Modus-Pin. Für Karten typisch (bewusst abweichende Fläche):

```html
<section data-theme="cole-tint-surface-warm" class="bg-surface">
  <p class="text-content-text">Standard-Theme der Section …</p>
  <article data-theme="cole-tint-surface-snow" class="bg-surface">   <!-- Card hebt sich ab -->
    <button class="bg-btn-primary-bg text-btn-primary-label">Sonder-CTA</button>
  </article>
</section>
```

## 4 Ausnahmen — folgen NICHT dem 4-Modi-Schema

Drei Kategorien laufen bewusst **nicht** über `data-theme`.

**a) Single-mode: Filter Panel, Search, Sustainability Tags, NutmixerTags**
Feste Werte, die nie theme-en → in `:root` definieren und **nicht** unter `[data-theme]` neu setzen:

```css
:root {
  --filter-chip-bg: var(--purple-early-evening-sky-40);
  --filter-chip-label: var(--purple-tint-light-old);
  --search-bg: var(--snow-white-90);
}
@theme inline {
  --color-filter-chip-bg: var(--filter-chip-bg);
  --color-filter-chip-label: var(--filter-chip-label);
  --color-search-bg: var(--search-bg);
}
```

```html
<div class="bg-filter-chip-bg text-filter-chip-label">Bio</div>
```

→ `bg-filter-chip-bg` sieht in jeder Section gleich aus (Opt-out per Weglassen des Theme-Overrides). Kein Variant nötig.

**b) Lively-Theme-Achse: Clrs / Mega Cards (MegaCard + LG/Primary + LG/Inline)**
Eine **zweite, orthogonale** Theming-Dimension (welche Kampagne), unabhängig von hell/dunkel. Zwei Dinge halten sie konfliktfrei:

- **Eigener Namespace** (`--color-megacard-btn-primary-*`, `--color-megacard-*`) — kollidiert nicht mit den globalen Tokens. Deshalb behält ein Kampagnen-Element seine Farben in *jeder* `data-theme`-Section.
- In Figma ist es eine **Varianten-Property** `Variant` an der Komponente (nicht ein Section-Pin) → im Code ein Attribut `data-lively-theme` pro Komponente, nicht `data-theme`.

| Figma: Variante von `Cards / MegaCard` | Code: `data-lively-theme` |
|---|---|
| `blue-green` | `blue-pistacio-green` (Default) |
| `orange-black` | `orange-black` |
| `happy-yellow` | `happy-christmas` |
| `purple-black` | `purple-black` |

```css
@theme inline {
  --color-megacard-btn-primary-bg: var(--megacard-btn-primary-bg);
  --color-megacard-btn-primary-label: var(--megacard-btn-primary-label);
}
/* Kampagne wird pro Komponente gewählt — wie die Figma-Variante */
:root,
[data-lively-theme="blue-pistacio-green"] {
  --megacard-btn-primary-bg: var(--sky-blue-90);
  --megacard-btn-primary-label: var(--pistachio-green-95);
}
[data-lively-theme="orange-black"] {
  --megacard-btn-primary-bg: var(--purple-tint-light-old);
  --megacard-btn-primary-label: var(--warm-white-80);
}
```

```html
<button data-lively-theme="orange-black"
        class="bg-megacard-btn-primary-bg text-megacard-btn-primary-label">Jetzt shoppen</button>
```

Jeder `data-lively-theme`-Wert setzt einen kompletten Satz Variablen, auch das ausgestanzte Label.

**c) Special-Achse: Clrs / Special (Voucher, Banner)**
Dritte parallele Achse (`data-special-theme`, Werte `forest`/`lilac`) für einzelne Sonderflächen. Eigener Namespace `--special-*`, kollidiert nicht mit den globalen Tokens.

```css
@theme inline {
  --color-special-surface-color-voucher: var(--special-surface-color-voucher);
  --color-special-content-text: var(--special-content-text);
}
[data-special-theme="lilac"] {
  --special-surface-color-voucher: var(--lilac-purple-90);
  --special-content-text: var(--purple-tint-dark-dark);
}
```

```html
<div data-special-theme="lilac" class="bg-special-surface-color-voucher text-special-content-text">…</div>
```

→ `forest` ist Default (Cards / VoucherCard), `lilac` wird pro Frame gesetzt (Layout / PromoBar).

## 5 Welche Achse wofür

| Achse | Attribut | wird gesetzt | Beispiel-Collections |
|---|---|---|---|
| Marke × Fläche (global) | `data-theme`, 4 Werte | am Container, kaskadiert | Clrs / Color Modes |
| Lively Theme (parallel) | `data-lively-theme`, 4 Kampagnen | pro Komponente | Clrs / Mega Cards (Karte + LG-Buttons) |
| Special (parallel) | `data-special-theme`, `forest`/`lilac` | pro Frame/Komponente | Clrs / Special (Voucher, Banner) |
| Single-mode | — (fix in `:root`) | nirgends | Filter Panel, Search, Sustainability Tags, NutmixerTags |

MegaCard und die LG-Buttons darin liegen in **einer** Collection und schalten gemeinsam:
ein `data-lively-theme` am Section-Wrapper setzt Karte *und* Button. Die Modi heißen daher nach
der Kampagne (`blue-pistacio-green`, `orange-black`, `happy-christmas`, `purple-black`) und
tragen keine Gruppen-Präfixe.

Technisch ist das ein und derselbe Mechanismus: ein Attribut-Selektor, der einen Satz Custom
Properties neu setzt — gleiche Spezifität, gleiche Vererbung. „Lively Theme" ist deshalb keine
eigene Technik, sondern eine **zweite, parallele Theme-Achse**.

Kombinierbar sind sie, weil die Token-Namespaces disjunkt sind (`--surface-*`, `--content-*`,
`--btn-*` vs. `--megacard-*` vs. `--megacard-btn-primary-*`): ein Element darf beide Attribute tragen,
jedes wirkt nur auf seine eigenen Tokens. Single-mode-Tokens stehen ausschließlich in `:root`
und werden in keinem `[data-theme]`-Block erneut gesetzt — genau das ist ihr Opt-out.

**Faustregel:** variiert ein Wert mit Marke oder Fläche → `data-theme`. Variiert er unabhängig
davon (Kampagne, Saison) → eigene Achse mit eigenem Token-Präfix. Variiert er nie → `:root`.

## 6 Die drei Regeln (spiegeln Figma)

1. **Keine primitiven Farben in der Komponente** — kein `bg-[#1d2020]` / `bg-cole-tint-90`, immer das semantische Utility (`bg-btn-primary-bg`).
2. **Theme am Container** (`data-theme`) — der eine Schalter kaskadiert; in bestimmten Komponenten ist das Theme aber explizit gesetzt (lokaler Override, siehe §3). Kampagne und Single-mode laufen dagegen pro Komponente (`data-lively-theme` bzw. fix in `:root`).
3. **Die Farb-Logik liegt in den Token-Definitionen, nicht im Komponenten-Code.** Die themeabhängige Belegung der Werte — z. B. Inputs und Fließtext = `purple-tint-dark`, Buttons und Akzente = `purple-tint-light` im Purple-Theme (siehe [2.1 Farbsystem](2.1-farbsystem.md), „Unregelmäßigkeiten“) — steckt ausschließlich in den Werten der semantischen CSS-Variablen je `data-theme`. Das Komponenten-Markup referenziert stets dasselbe semantische Utility und bleibt über alle Themes hinweg unverändert.
