# Technical Workflow: Using Claude + Figma MCP Reliably

**Status:** Best practice based on real-world tests (May 2026, updated August 2026)
**Author:** Claude + user feedback
**Goal:** Edit Figma files reliably in real time
**Scope:** process — pre-flight, font policy, verification, error handling, fallbacks, reporting. API behavior & code patterns: `1.3-figma-api-reference.md`. Setup: `1.1-figma-schreibzugriff-use_figma.md`.

---

## 🎯 Core principle (updated 2026-07-15)

**For the remote MCP (`use_figma` via the Figma connector), `fileKey` is the real target.** The file does **not** need to be open in Figma — the remote server runs server-side. Setup & details: `1.1-figma-schreibzugriff-use_figma.md`.

> **Legacy note:** The earlier rule "the active Figma tab is the real target, `fileKey` is just a reference" applied to the **local Dev Mode server** (127.0.0.1:3845, read-only). It no longer applies to `use_figma`.

### `setCurrentPageAsync()` — switching pages via code

Claude can switch the active page via code, regardless of which page the user currently has open:

```javascript
const page = figma.root.children.find(p => p.name === "CV EN");
await figma.setCurrentPageAsync(page);
// From here on Claude works on this page — even without any user action
```

**Consequences:**
- Claude can edit pages the user isn't currently looking at
- If the user has the file open, they may see a sudden page switch — this can be confusing
- **The page context resets between `use_figma` calls** to the first page — switch **at most once** per call; split multi-page work across separate calls
- The sync setter `figma.currentPage = page` does **not** work in `use_figma` (throws an error) — always use the async variant

## 1️⃣ PRE-FLIGHT CHECKLIST (before every edit)

### A) Check server status
```
Claude → Figma:get_metadata(fileKey=...)
         ↓
         Responds with XML? → ✅ API is up
         Error? → ❌ API unavailable
```

### B) Verify the target file
**Remote MCP (`use_figma`):** have the user provide the file URL / `fileKey` and cross-check with `get_metadata`. No open tab needed.
**Legacy (local Dev Mode server):** have the user activate the right Figma tab and verify.

### C) Run a test operation
```javascript
// ALWAYS run a mini test first (don't forget to load the font!):
await figma.loadFontAsync({ family: "Inter", style: "Regular" });
const page = figma.currentPage; // ← target the PAGE, not root!
const testNode = figma.createText();
testNode.characters = "[VERIFY_FIGMA_WRITE_WORKS]";
testNode.x = 200; testNode.y = -200; // away from (0,0), not on top of existing content
page.appendChild(testNode);
return { createdNodeIds: [testNode.id] };
```

**User checks:** Do I see `[VERIFY_FIGMA_WRITE_WORKS]` anywhere in the file?
- ✅ Yes → proceed with real edits (delete the test node afterward!)
- ❌ No → check write permissions → fallback strategy (below)

## 2️⃣ FONT LOADING (the main problem)

> **When font loading is needed at all** (only for `characters`/font-property/text-style mutations — NOT for fills, variable rebinds, or mode pins) and the server-side-font-inventory root cause: `1.3-figma-api-reference.md` §1️⃣. This section is the canonical **policy & recipes** for when you DO need it.

### Standard pattern (safe)
```javascript
async function loadAllFontsInNode(node) {
  // getStyledTextSegments returns all fonts in the node — faster than a character loop
  const segments = node.getStyledTextSegments(['fontName']);
  for (const seg of segments) {
    try {
      await figma.loadFontAsync(seg.fontName);
    } catch (e) {
      // Font unavailable — fallback needed (see below)
    }
  }
}
```

### ⚠️ Correction 2026-07-15: do NOT fall back to Inter for server-side-unavailable custom fonts

**Root cause, more precisely than "broken font":** custom fonts like "BROWN NOW TWO" are typically registered locally in the user's Figma client (Font Book / Font Helper) and render fine there. `use_figma` runs server-side on Figma's remote MCP infrastructure, which has its own, separate font inventory — locally registered custom fonts simply aren't installed there, regardless of the font rendering fine in the user's client.

**The "Inter fallback" below is an antipattern:** forcing `node.setRangeFontName(...)` to a different font — even just as a catch-block attempt — strips the `textStyleId` binding from any text node that has one (`textStyleId` silently resets to `""`). This happens even when the actual mutation you wanted (e.g. `setBoundVariable('characters', ...)`) would have succeeded cleanly without throwing.

**Correct approach when the font isn't loadable server-side:**
1. Do NOT attempt an Inter (or other substitute font) `loadFontAsync` fallback if the text node already has a `textStyleId`.
2. Reset the style directly, with no prior `loadFontAsync` call:
```javascript
textNode.textStyleId = originalStyleId; // works without loadFontAsync, even when the font is unavailable server-side
```
3. When changing text via an already-bound variable (`textNode.boundVariables.characters`), prefer `setBoundVariable()` (see `1.3-figma-api-reference.md` §1️⃣) — no font loading needed at all.

**Verified 2026-07-21 — safe plain-text edit despite server-side-unavailable font (Inter detour WITH style restore):** the Inter detour IS safe when — and only when — you explicitly re-assign the text style afterwards:

```javascript
const styleId = textNode.textStyleId;          // save
await figma.loadFontAsync({ family: "Inter", style: "Regular" });
textNode.setRangeFontName(0, textNode.characters.length, { family: "Inter", style: "Regular" });
textNode.characters = newText;                 // legal now — Inter is loaded
textNode.textStyleId = styleId;                // restore — works without font load
```

For variable-bound text, `setBoundVariable()` remains the better path (no font handling at all). The antipattern warning in this section applies to the detour WITHOUT the final restore step.

Keep the old fallback function below only as a documented anti-example — do not apply it to text nodes carrying a `textStyleId`:

### ~~Aggressive fallback (for broken fonts)~~ — antipattern, see correction above
```javascript
async function setTextSafely(node, newText) {
  await loadAllFontsInNode(node);
  try {
    await figma.loadFontAsync({ family: "Inter", style: "Regular" });
    node.setRangeFontName(0, node.characters.length, { family: "Inter", style: "Regular" });
  } catch (e) {
    // Inter also unavailable — signal abort via return
  }
  node.characters = newText;
}
```

## 3️⃣ CHANGING TEXT (workflow)

### Safe batch operation
```javascript
async function batchUpdateTexts(updates) {
  // getNodeById (sync) is deprecated and throws in use_figma — always use the async variant!
  for (const update of updates) {
    const node = await figma.getNodeByIdAsync(update.nodeId);
    if (node && node.type === 'TEXT') await loadAllFontsInNode(node);
  }
  
  let changedCount = 0;
  const errors = [];
  for (const update of updates) {
    try {
      const node = await figma.getNodeByIdAsync(update.nodeId);
      if (node && node.type === 'TEXT') {
        const newText = node.characters.replace(update.oldText, update.newText);
        if (node.characters !== newText) {
          node.characters = newText;
          changedCount++;
        }
      }
    } catch (e) {
      errors.push(update.nodeId + ": " + e.message); // NOT console.log — invisible!
    }
  }
  
  return { changedCount, errors };
}
```

## 4️⃣ VERIFICATION (not via console.log!)

### ❌ Wrong: console.log
```javascript
console.log("Update done"); // Claude does NOT see this!
```

### ✅ Right: return value (use_figma)
```javascript
return { changedCount: 5, nodeIds: [...] }; // Claude sees ONLY the return value
```

### ✅ Right: get_metadata / screenshot
```javascript
Figma:get_metadata(fileKey, nodeId)  // structure as XML
await node.screenshot()              // visual check directly inside the use_figma call
```

### ✅ Right: user confirmation
```
Claude: "Check whether X changed"
User:   "Yes" or "No"
```

## 5️⃣ ERROR HANDLING

| Error | Cause | Fix |
| --- | --- | --- |
| "Cannot write to node with unloaded font" | Font not loaded | `loadFontAsync()` before `node.characters = ...` |
| "Cannot unwrap symbol" | Custom font registered locally in the user's Figma client, not installed server-side for `use_figma` | Reset `textNode.textStyleId` directly, WITHOUT an Inter fallback (see correction 2026-07-15 in section 2️⃣) |
| "Setting figma.currentPage is not supported" | Sync setter used | `await figma.setCurrentPageAsync(page)` |
| "This resource couldn't be accessed" | Remote: wrong fileKey / no permission. Legacy: wrong tab active | Check fileKey, or have the user switch tabs |
| "No response from get_metadata" | API not responding | Check connector connection / MCP server |
| Text doesn't visibly change | Browser cache | User: refresh (F5) or close/reopen the file |

## 7️⃣ REPORTING RESULTS TO THE USER

When listing nodes or components for the user (tables, findings, block inventories): every row needs a Figma deep link — `https://www.figma.com/design/<fileKey>/?node-id=<X-Y>` (node-id with dash) — or at least the exact layer/component name so the user can find it via Figma search. Bare node IDs are useless to her: the Figma UI has no lookup for them. (User feedback, 2026-07-21.)

## 📋 SUMMARY: the 5 golden rules

1. **fileKey is what counts (remote MCP)** – the file doesn't need to be open; Claude switches pages via `setCurrentPageAsync()` (max. once per call)
2. **Fonts are the main problem** – `getStyledTextSegments(['fontName'])` + `loadFontAsync()` is not optional (but only for text mutations — see 1.3 §1️⃣)
3. **console.log is invisible** – use the `return` value or `get_metadata()` for verification
4. **Verify, don't trust** – check after every update (screenshot, metadata, or the user)
5. **No "done" without proof** – confirm first, then continue

### ⚠️ What does NOT work
- ❌ console.log() as feedback
- ❌ figma.notify() (throws "not implemented")
- ❌ Sync APIs `figma.getNodeById()` / `getLocalVariableCollections()` / `getStyleById()` — use the async variants
- ✅ ~~Creating/editing variables~~ **works since `use_figma`** (previously ❌) — see `1.3-figma-api-reference.md` §2️⃣

## 🆕 Environment findings

### 2026-07-16 session

**Local Dev Mode MCP tools can hang for minutes if the file isn't actively open in the desktop app.** `get_design_context` ran into a ~4-minute timeout with no fast error. `use_figma` (remote) worked regardless. Mitigation: if a local read tool hangs, fall back to reading via `use_figma` instead of retrying the same call.

**Chrome browser-automation session dropped mid-task (GitHub web editor), cause unconfirmed.** Several tool calls timed out (~4 min each), then the tab group was gone. Possible causes include the user's machine going to sleep, a network interruption, a tool/usage limit, or genuine extension instability — none of these were confirmed, so avoid asserting a specific cause when this happens again. Practical mitigation: don't bundle the final "Commit changes" click with other actions in the same batch call — click it alone and confirm success with a separate screenshot before considering the edit safely committed. Also assume in-progress, uncommitted editor content can be lost if the tab group disappears — re-fetch the file fresh before retrying rather than assuming your last known state still holds. (Web-editor techniques: `3-claude-meta/3.1-github-web-editor-notes.md`.)

*(The API-level findings from this session — `componentProperties` key suffixes, `getLocalVariableCollectionsAsync` for ID discovery — moved to `1.3-figma-api-reference.md` §2/§3, 2026-08-03.)*

### 2026-07-25 session (Cowork, model: claude-opus-4-8)

**`get_screenshot`'s "download the PNG via curl" path does NOT work in the Cowork bash sandbox.** The sandbox routes outbound HTTPS through a forward proxy (`127.0.0.1:3128`) that rejects `CONNECT` to non-allowlisted hosts with `HTTP 403 Forbidden`, surfacing as `curl: (56) Received HTTP code 403 from proxy after CONNECT`. Verified 2026-07-25 for BOTH the screenshot URL host `www.figma.com` AND `raw.githubusercontent.com` — so it is a general host-allowlist restriction, not Figma-specific, and not the short-lived screenshot URL expiring. Do NOT retry curl/wget or switch hosts as a "workaround".

Practical rules in Cowork:

- To actually SEE a `get_screenshot` result, set `enableBase64Response: true` (returns the image inline), or render inline inside a `use_figma` call via `await node.screenshot()`. The default URL+curl download path from bash is unavailable here.
- To read repo/reference files, use the `web_fetch` MCP tool — it takes a different network path and works; bash `curl` to the same raw URL does not. **But:** `web_fetch` on raw URLs can serve DAYS-stale content — verify freshness or fetch pinned to a commit SHA (details: `3-claude-meta/3.1-github-web-editor-notes.md`).
- This is a Cowork-sandbox trait. The older workflow notes assumed a shell where curl to arbitrary hosts works (Claude Code context); that assumption does not hold in Cowork.

**A single component variant can become write-locked against explicit variable-mode pins — silently, no error.** (Footer set `6315:16206`, variant `Variant=Default, window-w=max 963` / `6814:21204`.) `variant.setExplicitVariableModeForCollection(collection, modeId)` returns without throwing (`setError = null`), yet the pin never lands: `explicitVariableModes` stays `{}` and the resolved value is unchanged. Figma's own Dev-Mode mode dropdown can't switch it either — so it's a corrupted node state, not just an API quirk.

- **Judge by ground truth, not the getter.** `node.explicitVariableModes` reads stale here. Confirm success via the actually resolved color — `variable.resolveForConsumer(node).value` (real hex) plus `node.resolvedVariableModes[collectionId]`. Do NOT judge by screenshot alone: warm-white (`#fff9f2`) and snow-white (`#ffffff`) look near-identical, and a still-warm render was twice misread as switched.
- **Probe whether the node is globally locked.** Try pinning ANY other collection (e.g. a Width collection) — if that also stays `{}`, the node rejects all pins, not just one collection. Sibling variants (`min 964` / `max 520`) accepted their own pins normally, so it's variant-specific.
- **Workaround (non-destructive): pin one level up, on the COMPONENT_SET.** `set.setExplicitVariableModeForCollection(cm, modeId)` lands cleanly there and the write-locked variant inherits it (verified: surface resolved fresh to `#ffffff` = snow). Redundant own-pins on the sibling variants don't conflict. Regaining independent pinning on the variant needs a UI rebuild (Cmd+D duplicate) — risky for live instance links, so only on request.
