## 🧩 SLOTS & component properties in variant sets — NEW 2026-07-22

**Tested on:** ContentModules / Basic (7565:24446) + Section / CustomSection (7601:22036), Tarabao B2C file.

**Design rule (from the user, 2026-07-22): slot constructions REQUIRE a variant axis with ≥2 values** — each variant carries the slot with different default content (e.g. CustomSection: `Property 1=CustomContent|Variant2`). Exposed nested variants need NO extra axis. An axis on a slot set is therefore NOT redundant — never recommend deleting it.

**Identical variant names break the whole set:** if two or more variants share the exact same `Prop=Value` combination, Figma flags "Component set has existing errors" and `componentPropertyDefinitions` THROWS on read. Fix: rename the variant children to distinct combos (`variant.name = 'Has Headline?=True, TypeOfHeadline=H2-Default'`) — the error clears immediately.

**Slot properties multiply per variant when created via UI:** creating slots variant-by-variant produced 8 set-level SLOT properties ("Slot"…"Slot 8") for what should be 2 shared ones. Same-named slot props do NOT auto-merge. Consolidation recipe (all calls on the COMPONENT_SET):

```javascript
const key = set.editComponentProperty('Slot 2#7640:5', { name: 'Headline' }); // returns the NEW key
slotNode.componentPropertyReferences = { slotContentId: key };               // rewire EVERY slot node to the surviving key
set.deleteComponentProperty('Slot 3#7640:10');                               // then drop each orphaned prop
```

**Preferred values work on SLOT properties:** `set.editComponentProperty(key, { preferredValues: [{ type: 'COMPONENT_SET', key: node.key }] })` — `node.key` also works for unpublished local components.

**Slot API basics:** slot nodes are `type: 'SLOT'`; the binding reference key is `slotContentId`; `component.createSlot()` auto-creates a linked property; `instance.setProperties({[slotKey]: …})` throws — populate slots by appending children into the slot node.

## ⚠️ Further critical gotchas (from the "Button with Labels" → "Buttons/MD/PrimaryButton" migration project, 82 instances)

**Atomicity is per script, not per batch item:** an uncaught `throw` on ONE line rolls back the ENTIRE `use_figma` execution — even mutations that already ran successfully (e.g. an earlier `swapComponent()`) get discarded if a LATER line in the same call fails (e.g. `loadFontAsync()` for an unavailable font). For batch operations across many nodes: wrap each individual mutation in its own try/catch, otherwise a single failure at the end can silently undo the entire batch.

**Master-vs-instance cascade with plain IDs:** a node ID without a semicolon (e.g. `3238:10792`) isn't automatically a standalone top-level instance — it can sit structurally INSIDE a shared master component/component set (check the ancestor chain: `COMPONENT`/`COMPONENT_SET` before `PAGE`). A `swapComponent()` on such a node changes the shared template and automatically cascades to EVERY instance in the file using that exact variant — including instances that were explicitly not meant to be touched. Before batch swaps on plain IDs, always check the ancestor chain and the blast radius (how many other instances share the same `mainComponent.id`). Small comfort: reactions reliably survive such a swap, since they're node-bound, not component-bound.

**"Preferred values" ≠ slot property type:** preferred values on an instance-swap property only curate the suggestion list at swap time (not a hard lock) and must be edited on the main/set component via the EXISTING property. Don't create a second, competing property via "Create property" from a new instance selection — that leaves the old property marked as "unused".

**Detecting orphaned instances:** deleting a master component does NOT automatically delete its instances — they remain with their last visual state (possibly flagged as "missing component"). Check via `await instance.getMainComponentAsync()`.

**Addendum 2026-07-20 — a stale instance display name is NOT proof of orphaning:** an instance's display name can stay outdated even when the main component was never deleted but only reorganized/renamed — Figma does not rename existing instances retroactively. Example (Tarabao B2C): an instance named "Checkout / Block / Welcome/…" inside "Payment" looked orphaned, but its main component was intact and had merely been moved to "Components / Checkout / Identification". Before classifying an instance as orphaned, always resolve `await instance.getMainComponentAsync()` and compare against the CURRENT main component name/location; optionally rename the instance to match (done here on both affected Checkout-Welcome screens).

**Orphan-check methodology — compare against `componentPropertyDefinitions`, not just `variantGroupProperties`:** `variantGroupProperties` on a component set contains ONLY the variant axes (State/Type/window-w etc.). Text, boolean and instance-swap properties live in `componentPropertyDefinitions` of the set. An audit that compared instance properties only against `variantGroupProperties` produced 7 false positives in a single session (Filter Chip, Disclosure, DeliveryAddress, CardRow, Cards/Featured, VoucherCard, InputText — all correctly used properties, no real findings). Rule: for orphan/consistency checks always use the full property list via `(await instance.getMainComponentAsync()).parent.componentPropertyDefinitions`.

### ⚠️ Variant properties (especially color mode) aren't guaranteed compatible
Before swapping, read the source instance's variant properties (`instance.variantProperties`), especially the color mode (property name usually starts with `color-mode`). Color modes are often NOT named 1:1 across component families — example from this test: LG uses `color-mode: orange-cole-tint?`, MD uses `color-mode: cole-tint-warm-white?`. After the swap, check whether the target component (component set) offers a property with the same name:
```javascript
const sourceColorMode = Object.entries(instance.variantProperties).find(([k]) => k.startsWith('color-mode'));
const targetDefs = targetComponentSet.componentPropertyDefinitions; // the set, not the variant
const hasMatch = sourceColorMode && targetDefs[sourceColorMode[0]];
```
**Important:** if there's no match, do NOT silently fall back to the target component's default. Instead flag it explicitly in the `use_figma` return value (e.g. `colorModeCarriedOver: false, sourceColorMode: '...'`) and/or tell the user, so the right color mode can be checked/chosen manually.

**⚠️ Addendum 2026-07-14:** some component variants offer only ONE allowed value for color mode (e.g. `Buttons/MD/SecondaryButton` has only `color-mode: cole-tint-transparent ?` with a single option, `True`, unlike `Buttons/MD/PrimaryButton` with 3 selectable modes). In that case, "change color mode" isn't technically possible — check `variantOptions.length` on the target property first and report transparently instead of attempting a switch.

## 🔀 COMPONENT SWAP & ICON SELECTION (lossless) — NEW 2026-07-13

**Tested on:** 2026-07-13, Tarabao B2C-und-CI file, Buttons/LG/PrimaryButton → Buttons/MD/PrimaryButton.

### Lossless component swap
```javascript
const targetVariant = await figma.getNodeByIdAsync(variantNodeId); // the specific variant, not the set
instance.swapComponent(targetVariant);
instance.setProperties({ 'Show Icon?': 'True' /* + other variant properties */ });
```
Reactions (`reactions`) survive the swap. Also observed: `CHANGE_TO` reactions that pointed to a variant of the OLD component (e.g. hover state) get automatically remapped by Figma to the corresponding variant of the NEW component — reproduced twice, not officially guaranteed in the Plugin API docs.

**⚠️ Addendum 2026-07-14:** this automatic remapping has now also been confirmed across completely different component families (Primary→Secondary, not just within the same size family like LG→MD) — see `1.2-figma-workflow-technisch.md`, section 8c.

### ⚠️ Use the master component, not a remote copy
`search_design_system` + `importComponentByKeyAsync`/`importComponentSetByKeyAsync` can return a **detached remote copy** (`node.remote === true`, no parent on a real page) for libraries that live in the same file. This copy can be stale if the library was edited locally since the last "Publish" — in our test, a nested icon set in the remote copy was still called "Icons/Julia/Cart" (cart icons only), while the real, current master component in the file had long since moved to "Icons / ButtonIcons" (Cart/Delivery/Heart/Checkout/Log In).

**Practical rule:** check `.remote` on the target node before every swap. If `true`: look for the real master component directly in the file instead, e.g. on the "COMPONENTS & SCREENS" page:
```javascript
const page = await figma.getNodeByIdAsync(pageId);
await figma.setCurrentPageAsync(page);
const master = page.findAllWithCriteria({ types: ['COMPONENT_SET'] })
  .find(n => n.name === 'Buttons / MD / PrimaryButton' && n.remote === false);
```

### Non-exposed icon slots
Not every icon placeholder is a `componentPropertyDefinitions` property (instance swap). If `componentPropertyReferences` on the nested icon instance is empty (`{}`), there's no exposed property — the icon has to be swapped directly via the nested instance:
```javascript
const iconInstances = instance.findAllWithCriteria({ types: ['INSTANCE'] })
  .filter(n => n.name === 'Icons / ButtonIcons');
iconInstances.forEach(i => i.swapComponent(targetIconVariant));
```
For ambiguous or unexpectedly limited icon options (e.g. only cart states for a checkout button), better to ask briefly than to guess.

**⚠️ Addendum 2026-07-14 — icon instance name is NOT consistent across button families:** the nested icon instance name ("Icons / ButtonIcons" above) only applies to `Buttons/MD/PrimaryButton`. `Buttons/MD/SecondaryButton` uses a structurally completely different instance for the same "Show Icon?" slot, named "Icons / CartLive" (a cart badge system with properties like `Add to cart?`, `One Item?`, `Zero Items?`, `2 Items?`). A swap script that carries over the name from the source family finds **no matching instance** after a component swap between different families — it fails silently (no error, but the result stays empty/null). After every component swap between different families, ALWAYS re-list the nested instances via `findAllWithCriteria` and check the actual name instead of assuming it.

### Rebinding a text variable directly (no font loading needed)
```javascript
textNode.setBoundVariable('characters', targetVariable);
```
Works **without** a prior `loadFontAsync()`, even if the text node's current font is broken/unavailable (tested with a broken custom font). Applies both to switching modes on a variable and to fully rebinding to a different variable.

**⚠️ Addendum 2026-07-14, corrected 2026-07-15 — data layer ≠ visible rendering for server-side-unavailable custom fonts:** more precise root cause than "broken font": custom fonts like "BROWN NOW TWO" are registered locally in the user's Figma client and render fine there. `use_figma` runs server-side on Figma's remote MCP infrastructure with its own, separate font inventory — such locally registered fonts simply aren't installed there. The call therefore throws no error, and `textNode.characters` immediately reads back the new value correctly — but the `get_screenshot` render still showed the OLD text in this case, even after re-rendering multiple times. An explicit `figma.loadFontAsync({family: "BROWN NOW TWO", style: "TWO"})` attempt fails with `"font family does not exist"` — the font simply doesn't exist in the server-side `use_figma` context, regardless of the user's client.

**⚠️ Important correction 2026-07-15 — do NOT fall back to Inter:** don't work around this by falling back to `figma.loadFontAsync({family:"Inter", style:"Regular"})` + `node.setRangeFontName(...)` — this strips the `textStyleId` binding from any text node that has one (`textStyleId` resets to `""`), even though the actual `setBoundVariable` call would not have thrown. Correct: if a `textStyleId` is present, reset it directly (`textNode.textStyleId = originalStyleId`), with no prior `loadFontAsync`. **Practical rule:** tell the user that the change is technically applied correctly but the visible result may only show up later — and never force a substitute font like Inter via `setRangeFontName` on a text node carrying a `textStyleId`.

**Correction to the `__All Button Labels` structure:** contrary to an earlier assumption, this collection has **no modes per label** — only a single mode ("Mode 1"). Instead, each label text exists as its own STRING variable (e.g. "Weiter zur Bezahlung" as its own variable, not as a mode of "placeholder"). Before creating a new mode, always check first whether the desired label text doesn't already exist as its own variable.

### 🎯 Pattern: text override without font loading via variable modes
If a text layer is already bound to a variable (`textNode.boundVariables.characters` present), the visible text can be changed without writing `node.characters` directly — and therefore without `loadFontAsync()`, which otherwise fails for custom fonts (e.g. "BROWN NOW TWO"):

```javascript
// 1. Check whether the text layer is variable-bound
console.log(textNode.boundVariables); // { characters: { type: 'VARIABLE_ALIAS', id: 'VariableID:...' }, ... }

// 2. Get the variable + collection
const v = await figma.variables.getVariableByIdAsync(textNode.boundVariables.characters.id);
const coll = await figma.variables.getVariableCollectionByIdAsync(v.variableCollectionId);

// 3. Create (or reuse) a new mode and set the value
let mode = coll.modes.find(m => m.name === 'DesiredText');
const modeId = mode ? mode.modeId : coll.addMode('DesiredText');
v.setValueForMode(modeId, 'Desired Text');

// 4. Explicitly set the instance to this mode (applies to the whole instance/subtree)
instance.setExplicitVariableModeForCollection(coll, modeId);
// Result: textNode.characters now reads the new text -- without loadFontAsync(),
// original font is preserved.
```

**Limitations:**
- Only if `characters` is already bound to a variable (not for free text)
- `setExplicitVariableModeForCollection` applies to the whole instance/subtree — with several variable-bound properties in the same collection, all of them change together
- A new mode in a shared collection only affects instances that are explicitly switched to it

**⚠️ Addendum 2026-07-14, corrected 2026-07-15 — data layer ≠ visible rendering for server-side-unavailable custom fonts:** same applies to `textNode.setBoundVariable('characters', variable)` (direct rebind to another string variable, no mode switch): the call throws NO error when the text node's font isn't installed server-side (tested with "BROWN NOW TWO" — registered locally for the user, but not in `use_figma`'s separate remote font inventory), and `textNode.characters` immediately reads back the new value correctly. The `get_screenshot` render still showed the OLD text in this case — even after re-rendering multiple times. An explicit `figma.loadFontAsync({family: "BROWN NOW TWO", style: "TWO"})` attempt fails with `"font family does not exist"` — the font simply doesn't exist in the server-side `use_figma` context.

**⚠️ Important correction 2026-07-15 — do NOT fall back to Inter:** same rule applies here: don't fall back to a substitute font like Inter via `setRangeFontName` — this strips the `textStyleId` binding when one is set. Instead, set `textNode.textStyleId = originalStyleId` directly, without a prior `loadFontAsync`. **Practical rule:** tell the user the change is technically applied correctly but the visible result may only show up later.

## 1️⃣ TEXT OPERATIONS (✅ WORKS)

### Changing text
```javascript
async function updateText(nodeId, newContent) {
  const node = await figma.getNodeByIdAsync(nodeId);
  if (!node || node.type !== 'TEXT') return;
  const fontRef = node.getRangeFontName(0, 1);
  await figma.loadFontAsync({ family: fontRef?.family || 'Inter', style: fontRef?.style || 'Regular' });
  node.characters = newContent;
}
```

### Copying all typography properties
```javascript
async function copyAllTypography(source, target) {
  const font = source.getRangeFontName(0, 1);
  await figma.loadFontAsync({ family: font?.family || 'Inter', style: font?.style || 'Regular' });
  target.fontSize = source.fontSize;
  target.lineHeight = source.lineHeight;
  target.letterSpacing = source.letterSpacing;
  target.textCase = source.textCase;
  target.textDecoration = source.textDecoration;
  target.textAlignHorizontal = source.textAlignHorizontal;
  target.setRangeFontName(0, target.characters.length, { family: font?.family || 'Inter', style: font?.style || 'Regular' });
  if (source.fills?.length > 0) target.fills = JSON.parse(JSON.stringify(source.fills));
}
```

### `resize()` sets height to FIXED
After `node.resize(w, h)`, `textAutoResize` is set to `"NONE"` — the text no longer wraps automatically and the height doesn't adjust. For text nodes that should adapt to their content:
```javascript
node.resize(width, node.height);         // fix the width
node.textAutoResize = "HEIGHT";          // height hugs content
// or:
node.textAutoResize = "WIDTH_AND_HEIGHT"; // width and height hug content
```

## 3️⃣ GRID LAYOUT (✅ WORKS — watch for quirks)

**Tested on:** 2026-06-03

### Correct order (must be followed)
```javascript
frame.layoutMode = "GRID";
frame.gridColumnCount = 2;       // 1. count first
frame.gridRowCount = 1;          // 2. count first
frame.gridColumnSizes = [...];   // 3. then sizes
frame.gridRowSizes = [...];      // 4. then sizes
frame.gridColumnGap = 40;
frame.gridRowGap = 0;
```

### `gridItemsPositioning` — auto vs manual
```javascript
// ✅ ROW_AUTO_FLOW: children are placed into rows automatically (default)
frame.gridItemsPositioning = "ROW_AUTO_FLOW";

// ⚠️ MANUAL: every child needs setGridChildPosition() — often causes unwanted side effects
frame.gridItemsPositioning = "MANUAL";
child.setGridChildPosition(0, 0); // (rowIndex, columnIndex)
```
**Recommendation:** use `ROW_AUTO_FLOW` — children get placed automatically in order.

### Grid frame height — `counterAxisSizingMode`
```javascript
frame.primaryAxisSizingMode = "FIXED";  // fixed width
frame.counterAxisSizingMode = "AUTO";   // ✅ height hugs content (needs ROW_AUTO_FLOW)
frame.counterAxisSizingMode = "FIXED";  // ❌ height stays fixed — content can overflow
```

### Full-size grid frame with padding (preferred pattern)
Instead of a small, centered inner frame: a grid frame at full slide size with padding as margin.
```javascript
// ✅ Clean: grid fills the whole slide, padding creates spacing
frame.layoutMode = "GRID";
frame.resize(874, 595);          // slide size
frame.paddingTop = 78;
frame.paddingBottom = 78;
frame.paddingLeft = 78;
frame.paddingRight = 78;
frame.primaryAxisSizingMode = "FIXED";
frame.counterAxisSizingMode = "FIXED";
frame.x = 0; frame.y = 0;

// ❌ Cumbersome: a small inner frame has to be centered manually
inner.x = Math.round((slideW - inner.width) / 2);
inner.y = Math.round((slideH - inner.height) / 2);
```

### Rotated text as a direct grid child
Text nodes can be direct grid children (no wrapper frame needed). Position: x:0, y:[textWidth], rotation:90.
```javascript
const heading = figma.createText();
heading.characters = "CONTENT";
heading.fontSize = 63.6;
grid.appendChild(heading);

// After appendChild: y = original text width, rotation 90°
heading.x = 0;
heading.y = heading.width;  // y = text width (before rotation)
heading.rotation = 90;
```

## 🆕 New findings, 2026-07-16 session

**`componentProperties` keys carry generated suffixes** (e.g. `"Variant#1234:5"`, not plain `"Variant"`). Match with `Object.keys(props).find(k => k.startsWith('Variant'))` instead of expecting an exact key name.

**`figma.variables.getLocalVariableCollectionsAsync()`** lists every local variable collection and its variables — the way to find a target variable when its ID isn't known yet, since the user typically has no way to read out variable IDs herself.

**Local Dev Mode MCP tools (`get_design_context`, etc.) can hang for minutes if the file isn't actively open in the desktop app**, with no fast error. `use_figma` (remote) works regardless of desktop app state. Mitigation: fall back to `use_figma` for reads instead of retrying the same hanging call.
