## 0️⃣ EXECUTION MODEL (`use_figma`)

- **Atomicity is per script, not per batch item** — an uncaught `throw` on ONE line rolls back the ENTIRE `use_figma` execution, including mutations that already ran successfully (e.g. an earlier `swapComponent()` is discarded if a later `loadFontAsync()` fails). For batch operations: wrap each individual mutation in its own try/catch, otherwise a single failure at the end can silently undo the whole batch.
- **…but failed calls are NOT reliably atomic either** (2026-07-22): one throw left a stray cloned variant behind, another rolled back cleanly. After any failed mutating call: re-read the target, remove strays, then retry.
- **Page context resets between calls** to the first page — `await figma.setCurrentPageAsync(page)` at most once per call; split multi-page work across separate calls. The sync setter `figma.currentPage = page` throws. (Details: 1.2, Core principle.)
- **Output only via `return`.** `console.log()` is invisible to Claude; `figma.notify()` throws "not implemented". Return all created/changed node IDs.
- ❌ `figma.root.appendChild()` — use `page.appendChild()`.
- ❌ Sync APIs are deprecated and throw: `getNodeById`, `getLocalVariableCollections`, `getStyleById` — always use the async variants.

## 1️⃣ FONTS & TEXT

### When font loading is required — and when NOT (2026-07-22)

`loadFontAsync` is required **only** for mutations of `characters`, font properties, or text styles. It is **NOT** needed for:

- rebinding a TEXT node's fill via `setBoundVariableForPaint` + `fills` reassignment,
- `setExplicitVariableModeForCollection(...)` on a variant containing text,
- `textNode.setBoundVariable('characters', variable)`,
- resetting `textNode.textStyleId`.

Verified on Buttons/MD/PrimaryButton (2310:2156, label font "BROWN NOW TWO" MISSING in the environment): all of the above succeed with `hasMissingFont: true`. **Do NOT preemptively load fonts for pure fill/variable-mode operations** — if the font is missing, the unnecessary `loadFontAsync` throws and (atomicity, §0) rolls back the whole script.

For loading, use `getStyledTextSegments(['fontName'])` + `loadFontAsync()` per segment — canonical recipe and the full font policy live in **1.2 §2️⃣ FONT LOADING**.

### Server-side font inventory ≠ user's client (2026-07-14, corrected 2026-07-15)

Custom fonts like "BROWN NOW TWO" are registered locally in the user's Figma client (Font Book / Font Helper) and render fine there. `use_figma` runs server-side on Figma's remote MCP infrastructure with its own, separate font inventory — locally registered fonts simply aren't installed there. Consequences:

- `figma.loadFontAsync({family:"BROWN NOW TWO", style:"TWO"})` fails with `"font family does not exist"`, regardless of the font rendering fine in the user's client.
- **Data layer ≠ visible rendering:** `setBoundVariable('characters', …)` (and mode switches) throw NO error and `textNode.characters` immediately reads back the new value — but the `get_screenshot` render can keep showing the OLD text, even after re-rendering multiple times. **Practical rule:** tell the user the change is technically applied correctly but the visible result may only show up later.

### Inter fallback policy (2026-07-15, extended 2026-07-21)

- Forcing `node.setRangeFontName(...)` to a substitute font (Inter) — even just as a catch-block attempt — **strips the `textStyleId` binding** from any text node that has one (`textStyleId` silently resets to `""`), even when the mutation you actually wanted would have succeeded cleanly.
- If a `textStyleId` is present: reset it directly, no prior `loadFontAsync` needed — `textNode.textStyleId = originalStyleId`.
- **The Inter detour IS safe when — and only when — the style is explicitly re-assigned afterwards** (verified 2026-07-21; recipe in 1.2 §2️⃣): save `textStyleId` → load Inter → `setRangeFontName` → set `characters` → restore `textStyleId`.
- For variable-bound text, `setBoundVariable()` remains the better path (no font handling at all).

### Changing text
```javascript
async function updateText(nodeId, newContent) {
  const node = await figma.getNodeByIdAsync(nodeId);
  if (!node || node.type !== 'TEXT') return;
  const fontRef = node.getRangeFontName(0, 1);
  await figma.loadFontAsync({ family: fontRef?.family || 'Inter', style: fontRef?.style || 'Regular' });
  node.characters = newContent;
}
```

### Copying all typography properties
```javascript
async function copyAllTypography(source, target) {
  const font = source.getRangeFontName(0, 1);
  await figma.loadFontAsync({ family: font?.family || 'Inter', style: font?.style || 'Regular' });
  target.fontSize = source.fontSize;
  target.lineHeight = source.lineHeight;
  target.letterSpacing = source.letterSpacing;
  target.textCase = source.textCase;
  target.textDecoration = source.textDecoration;
  target.textAlignHorizontal = source.textAlignHorizontal;
  target.setRangeFontName(0, target.characters.length, { family: font?.family || 'Inter', style: font?.style || 'Regular' });
  if (source.fills?.length > 0) target.fills = JSON.parse(JSON.stringify(source.fills));
}
```

### `resize()` sets height to FIXED
After `node.resize(w, h)`, `textAutoResize` is set to `"NONE"` — the text no longer wraps and the height doesn't adjust. For text nodes that should adapt to their content:
```javascript
node.resize(width, node.height);          // fix the width
node.textAutoResize = "HEIGHT";           // height hugs content
// or:
node.textAutoResize = "WIDTH_AND_HEIGHT"; // width and height hug content
```

### Text styles: create & derive semantic roles

- **`figma.createTextStyle()` works via `use_figma`** (verified 2026-07-20) — Claude can create local text styles and bind them directly at node creation. **Library** styles cannot be created via the API, only transferred by ID (see 1.5).
- **Derive a text layer's semantic role from its text STYLE NAME (`getStyleByIdAsync`), not from font family or size** (2026-07-25):
```javascript
const t = await figma.getNodeByIdAsync(textId);
const styleName = (t.textStyleId && t.textStyleId !== figma.mixed)
  ? (await figma.getStyleByIdAsync(t.textStyleId))?.name   // e.g. "H2 Subtitle", "H1", "Cards/Featured/Title"
  : null;
```
Context (Tarabao B2C, 2026-07-25): the DiscoveryCard "Titel + Untertitel" lines shared their FONTS with several Headline primitives — LUMOSKY appears in BOTH `Primitives / Headline / H1` (style "H1", 48px) and `H2` (style "H2", 32px); BROWN NOW TWO in `H1 Subtitle` (40px) and `H2 Subtitle` (24px). Only the style name pins the correct level. Rule: for "where does this line belong" questions, resolve `textStyleId` → style name first.

### Text ↔ variables

- **Direct rebind without font loading:** `textNode.setBoundVariable('characters', targetVariable)` works without a prior `loadFontAsync()`, even if the node's current font is broken/unavailable. Applies both to mode switches and to fully rebinding to a different variable. (Rendering caveat: see server-side font inventory above.)
- **FLOAT variables cannot be bound to text via the API** (2026-07-22): `setBoundVariable('characters', floatVar)` throws `variable of resolved type 'FLOAT' cannot …` — even though the Figma UI allows it and pre-existing FLOAT→characters bindings render fine. When recreating such bindings programmatically, create the variable as STRING (use the exact previously rendered string, e.g. "12.60" not "12.6"). Discovered during the __Produkte migration (736 rebindings after the __Product Examples collection was deleted).
- **Text override via variable modes (no font loading):** if `textNode.boundVariables.characters` is present, the visible text can be changed without touching `node.characters`:
```javascript
const v = await figma.variables.getVariableByIdAsync(textNode.boundVariables.characters.id);
const coll = await figma.variables.getVariableCollectionByIdAsync(v.variableCollectionId);
let mode = coll.modes.find(m => m.name === 'DesiredText');
const modeId = mode ? mode.modeId : coll.addMode('DesiredText');
v.setValueForMode(modeId, 'Desired Text');
instance.setExplicitVariableModeForCollection(coll, modeId); // applies to the whole instance/subtree
```
Limitations: only for already-bound text; the explicit mode applies to the whole instance/subtree (several bound properties in the same collection change together); a new mode in a shared collection only affects instances explicitly switched to it. Context of discovery: Buttons/MD/PrimaryButton, layer "label" bound to "placeholder" in collection "__All Button Labels".
- **`__All Button Labels` structure:** the collection has NO modes per label — only a single mode ("Mode 1"); each label text is its own STRING variable (e.g. "Weiter zur Bezahlung"). Before creating a new mode, check whether the desired label already exists as its own variable.
- Workaround if the text layer is NOT variable-bound: `1.5-figma-stylesheet-workaround.md`.

## 2️⃣ VARIABLES

### Variables work (correction 2026-07-13)

The previous claim "completely blocked" was wrong — the cause was a bug in the test code (ID format `'4146:39881'` instead of `'VariableID:4146:39881'`), not a platform restriction. Live-tested and confirmed (Tarabao B2C-und-CI):

```javascript
// Reading — IMPORTANT: use the full "VariableID:" prefix!
const v = await figma.variables.getVariableByIdAsync('VariableID:xxxx:yyyy');
const coll = await figma.variables.getVariableCollectionByIdAsync(v.variableCollectionId);

// Writing — set a value for an existing mode
v.setValueForMode(modeId, 'new value');

// Create a new variable
const newVar = figma.variables.createVariable('Name', collectionId, 'STRING'); // or COLOR, FLOAT, BOOLEAN

// Add / remove a mode on a collection
const newModeId = coll.addMode('ModeName');
coll.removeMode(newModeId);
```

**Official reference:** [Working with Variables](https://developers.figma.com/docs/plugins/working-with-variables/), [Variables API](https://www.figma.com/plugin-docs/api/figma-variables/) — both confirm `createVariable`, `setValueForMode`, `addMode` as regularly supported Plugin API functions.

**Finding a variable when its ID isn't known:** `figma.variables.getLocalVariableCollectionsAsync()` lists every local collection with its variables — the user typically has no way to read out variable IDs herself, so guessing or asking her isn't a good fallback (2026-07-16).

### PERCENT values cannot be stored as variables for `lineHeight` / `letterSpacing` (2026-07-30)

A FLOAT variable bound to `lineHeight`/`letterSpacing` (on a text node OR a text style) is interpreted as PIXELS, regardless of the field's current unit — empirically tested: a variable holding `140` bound to a `{unit:'PERCENT', value:140}` line-height flipped the resolved value to `{unit:'PIXELS', value:140}`. A *relative* type scale therefore cannot be expressed as a shared variable at all. Store relative leading/tracking as PERCENT directly on the text styles — this is why the Tarabao B2C leading/tracking scale lives on the 62 text styles, not in a variable collection (see `2-tarabao/2.3-design-tokens-tailwind-v4.md` §5a). CSS side: Figma % ÷ 100 → unitless `line-height`, `em` `letter-spacing`.

### Getters can read stale — verify against ground truth

- **Text-style getters:** `getLocalTextStylesAsync()` / `style.lineHeight` returned an outdated value on a first read and the correct value seconds later (18 px vs. 115 % for the same style, both read-only, no edit in between; 2026-07-30). Don't treat a single getter read as ground truth — cross-check via a full re-scan of all styles, `node.height`, or `getStyledTextSegments(['lineHeight'])`.
- **Variable-mode pins:** `node.explicitVariableModes` can read stale, and a variant can silently reject pins entirely — judge by `variable.resolveForConsumer(node).value` (real hex) plus `node.resolvedVariableModes[collectionId]`, and pin on the COMPONENT_SET as workaround. Full write-lock finding: **1.2, New findings 2026-07-25**.

### Deleted variables/collections stay readable (2026-07-22)

Deleting a variable collection (or component) in the UI does NOT purge it — deleted variables remain fully readable via their IDs (`name`, `resolvedType`, `valuesByMode`, mode names via the deleted collection object), and deleted component sets persist as parentless ghosts invisible to every canvas scan. Consequences:

- (a) full reconstruction after an accidental delete is possible as long as bindings still reference the IDs — **harvest values BEFORE cleaning dangling bindings**;
- (b) usage counts via canvas scans miss ghost masters — resolve `getMainComponentAsync()` and check `parent === null`;
- (c) the Dev Mode view may keep showing the deleted collection's modes (stale) — verify against the Design-Mode variable panel instead.

**`explicitVariableModes` leftovers from deleted collections** ("Change variable mode" remnants) cause ghost collections in Dev Mode (see `2-tarabao/offene-punkte.md`, points 7/8). Verified cleanup (423 nodes, 0 failures, works on instance sublayers too): `getVariableCollectionByIdAsync(staleId)` still resolves deleted collections → walk the page, collect nodes whose `explicitVariableModes` keys are missing from `getLocalVariableCollectionsAsync()`, then `node.clearExplicitVariableModeForCollection(collectionHandle)`.

### Deleted-collection "ghost" modes in the Dev Mode picker — NOT fixable via the plugin API (2026-07-22)

**Symptom:** Dev Mode / component playground keeps showing an outdated variable mode (e.g. `__Product Examples · Auto (Product-1)`) even after multiple reloads.

**Diagnosis via plugin API:** `node.resolvedVariableModes` (guard with try/catch — it throws on PAGE/DOCUMENT nodes) lists **every collection consumed anywhere in the node's subtree**, each resolved to its applicable mode; a value shown as "Auto (…)" in the UI = the collection's **default** mode = consumed, not explicitly set. If a dead collection appears there but is NOT found in any of: `boundVariables`, instance `componentProperties[*].boundVariables`, styled text segments (`getStyledTextSegments(['boundVariables'])`), `componentPropertyDefinitions[*].boundVariables` (readable only on a COMPONENT_SET or non-variant COMPONENT), `explicitVariableModes` (node + full ancestor chain), or as an alias value of any live variable → then check `(await figma.variables.getVariableCollectionByIdAsync(deadId)).variableIds.length`. If it is **0**, the collection is fully deleted and only its mode records survive.

**Why the plugin API cannot fix it:** there is nothing left to unbind. `clearExplicitVariableModeForCollection` is a no-op (`explicitVariableModes` is `{}`), and there are no variables left to detach. The lingering entry is a garbage-collection remnant in Figma's internal resolved-mode index, not a live binding.

**Fix — the user must do this manually in Figma; Claude must NOT attempt an API fix:**
1. Switch to **Design mode** (the command does not exist in Dev Mode).
2. Open **Quick Actions** with `Cmd + /` → type **"Detach deleted variables"** → Enter. It lives ONLY in Quick Actions, not in the right-click context menu.
3. Run it on **every affected page**.
4. **Close the file for ~5 min** so Figma's garbage collection purges the orphaned mode records — a plain reload is not enough (the desktop app keeps the Dev Mode session alive).

**Verified 2026-07-22** (Tarabao B2C, `CMS / MediaText` + `CMS / CustomContentWithImg`): the collection `__Product Examples` had `variableIds.length === 0` (only modes Product-1/2/3 survived); no node consumed any of its variables. After the user ran "Detach deleted variables" (reported 26 connections removed), `resolvedVariableModes` on both component sets was clean of all dead collections — the remaining picker entry was pure Dev Mode display cache, cleared by the close-file GC step.

## 3️⃣ COMPONENTS, INSTANCES & SLOTS

### Lossless component swap (2026-07-13)

Tested: Buttons/LG/PrimaryButton → Buttons/MD/PrimaryButton (Tarabao B2C-und-CI).

```javascript
const targetVariant = await figma.getNodeByIdAsync(variantNodeId); // the specific variant, not the set
instance.swapComponent(targetVariant);
instance.setProperties({ 'Show Icon?': 'True' /* + other variant properties */ });
```

- **Reactions survive the swap** (they're node-bound, not component-bound). `CHANGE_TO` reactions that pointed to a variant of the OLD component (e.g. hover state) get automatically remapped by Figma to the corresponding variant of the NEW component — reproduced twice within the same size family, and confirmed 2026-07-14 across completely different component families (Primary→Secondary, frame "PRACTICE FOR CLAUDE"). Not officially guaranteed in the Plugin API docs.
- **Writing reactions:** `instance.reactions = [...]` is read-only and throws — use `await instance.setReactionsAsync(...)` (verified 2026-07-14).

### Master-vs-instance cascade with plain IDs

A node ID without a semicolon (e.g. `3238:10792`) isn't automatically a standalone top-level instance — it can sit structurally INSIDE a shared master component/component set (check the ancestor chain: `COMPONENT`/`COMPONENT_SET` before `PAGE`). A `swapComponent()` on such a node changes the shared template and cascades to EVERY instance in the file using that exact variant — including instances that were explicitly not meant to be touched. Before batch swaps on plain IDs, always check the ancestor chain and the blast radius (how many other instances share the same `mainComponent.id`).

### Use the master component, not a remote copy

`search_design_system` + `importComponentByKeyAsync`/`importComponentSetByKeyAsync` can return a **detached remote copy** (`node.remote === true`, no parent on a real page) for libraries that live in the same file. This copy can be stale if the library was edited locally since the last "Publish" — in our test, a nested icon set in the remote copy was still called "Icons/Julia/Cart", while the real master in the file had long since moved to "Icons / ButtonIcons". **Practical rule:** check `.remote` on the target node before every swap; if `true`, find the real master directly in the file:
```javascript
const page = await figma.getNodeByIdAsync(pageId);
await figma.setCurrentPageAsync(page);
const master = page.findAllWithCriteria({ types: ['COMPONENT_SET'] })
  .find(n => n.name === 'Buttons / MD / PrimaryButton' && n.remote === false);
```

### Non-exposed icon slots — and icon instance names differ per family

Not every icon placeholder is a `componentPropertyDefinitions` property (instance swap). If `componentPropertyReferences` on the nested icon instance is empty (`{}`), there's no exposed property — swap directly via the nested instance:
```javascript
const iconInstances = instance.findAllWithCriteria({ types: ['INSTANCE'] })
  .filter(n => n.name === 'Icons / ButtonIcons');
iconInstances.forEach(i => i.swapComponent(targetIconVariant));
```
**The nested icon instance name is NOT consistent across button families** (2026-07-14): "Icons / ButtonIcons" applies to `Buttons/MD/PrimaryButton`; `Buttons/MD/SecondaryButton` uses a structurally different instance named "Icons / CartLive" (a cart badge system with properties like `Add to cart?`, `One Item?`, `Zero Items?`, `2 Items?`). A swap script that carries the name over from the source family finds **no matching instance** — it fails silently (no error, empty/null result). After every cross-family swap, ALWAYS re-list the nested instances via `findAllWithCriteria` and check the actual names. For ambiguous or unexpectedly limited icon options, ask briefly rather than guess.

### Variant properties (especially color mode) aren't guaranteed compatible

Before swapping, read the source instance's variant properties (`instance.variantProperties`), especially the color mode (property name usually starts with `color-mode`). Color modes are often NOT named 1:1 across component families — e.g. LG uses `color-mode: orange-cole-tint?`, MD uses `color-mode: cole-tint-warm-white?`. After the swap, check whether the target set offers a property with the same name:
```javascript
const sourceColorMode = Object.entries(instance.variantProperties).find(([k]) => k.startsWith('color-mode'));
const targetDefs = targetComponentSet.componentPropertyDefinitions; // the set, not the variant
const hasMatch = sourceColorMode && targetDefs[sourceColorMode[0]];
```
If there's no match, do NOT silently fall back to the target's default — flag it explicitly in the return value (e.g. `colorModeCarriedOver: false, sourceColorMode: '...'`) and/or tell the user. **Some variants offer only ONE allowed value** (2026-07-14: `Buttons/MD/SecondaryButton` has only `color-mode: cole-tint-transparent ?` with the single option `True`) — check `variantOptions.length` on the target property first and report transparently instead of attempting a switch.

### Component property keys: suffixes & re-suffixing

- `componentProperties` keys carry generated suffixes (e.g. `"Variant#1234:5"`, not plain `"Variant"`) — match with `Object.keys(props).find(k => k.startsWith('Variant'))` (2026-07-16).
- Property keys get **re-suffixed by structural operations**: after `combineAsVariants` (and after user renames) a key like `Slot#7601:2` becomes e.g. `Text#7660:0`. Never carry keys across calls — re-read `componentPropertyDefinitions` fresh and select by `type` (`SLOT`, `VARIANT`, …) (2026-07-22).
- **"Preferred values" ≠ slot property type:** preferred values on an instance-swap property only curate the suggestion list at swap time (not a hard lock) and must be edited on the main/set component via the EXISTING property. Don't create a second, competing property via "Create property" from a new instance selection — that leaves the old property marked "unused".

### Orphan & consistency checks

- **Detecting orphaned instances:** deleting a master does NOT delete its instances — they keep their last visual state (possibly flagged "missing component"). Check via `await instance.getMainComponentAsync()`.
- **A stale instance display name is NOT proof of orphaning** (2026-07-20): display names stay outdated when the main component was merely reorganized/renamed — Figma doesn't rename instances retroactively. Example: an instance named "Checkout / Block / Welcome/…" looked orphaned, but its main component was intact and had moved to "Components / Checkout / Identification". Always resolve `getMainComponentAsync()` and compare against the CURRENT main component name/location; optionally rename the instance to match.
- **Compare against `componentPropertyDefinitions`, not just `variantGroupProperties`:** `variantGroupProperties` contains ONLY the variant axes. Text, boolean and instance-swap properties live in `componentPropertyDefinitions` of the set. An audit comparing only against `variantGroupProperties` produced 7 false positives in one session (Filter Chip, Disclosure, DeliveryAddress, CardRow, Cards/Featured, VoucherCard, InputText). Rule: always use `(await instance.getMainComponentAsync()).parent.componentPropertyDefinitions`.

### SLOTS & component properties in variant sets (2026-07-22)

Tested on: ContentModules / Basic (7565:24446) + Section / CustomSection (7601:22036), Tarabao B2C file.

- **Design rule (from the user, 2026-07-22): slot constructions REQUIRE a variant axis with ≥2 values** — each variant carries the slot with different default content (e.g. CustomSection: `Property 1=CustomContent|Variant2`). Exposed nested variants need NO extra axis. An axis on a slot set is therefore NOT redundant — never recommend deleting it.
- **Identical variant names break the whole set:** if two or more variants share the exact same `Prop=Value` combination, Figma flags "Component set has existing errors" and `componentPropertyDefinitions` THROWS on read. Fix: rename the variant children to distinct combos (`variant.name = 'Has Headline?=True, TypeOfHeadline=H2-Default'`) — the error clears immediately.
- **Slot properties multiply per variant when created via UI:** creating slots variant-by-variant produced 8 set-level SLOT properties ("Slot"…"Slot 8") for what should be 2 shared ones. Same-named slot props do NOT auto-merge. Consolidation recipe (all calls on the COMPONENT_SET):
```javascript
const key = set.editComponentProperty('Slot 2#7640:5', { name: 'Headline' }); // returns the NEW key
slotNode.componentPropertyReferences = { slotContentId: key }; // rewire EVERY slot node to the surviving key
set.deleteComponentProperty('Slot 3#7640:10'); // then drop each orphaned prop
```
- **Preferred values work on SLOT properties:** `set.editComponentProperty(key, { preferredValues: [{ type: 'COMPONENT_SET', key: node.key }] })` — `node.key` also works for unpublished local components. `editComponentProperty(key, { slotSettings })` works too; to set `allowPreferredValuesOnly`, pass the FULL `slotSettings` object merged from the current definition (`Object.assign({}, def.slotSettings, { allowPreferredValuesOnly: true })`).
- **Slot API basics:** slot nodes are `type: 'SLOT'`; the binding reference key is `slotContentId`; `component.createSlot()` auto-creates a linked property; `instance.setProperties({[slotKey]: …})` throws — populate slots by appending children into the slot node.
- **`clone()` of a variant containing a SLOT node converts the slot back to a plain FRAME** and silently drops its `slotContentId` binding. Re-bind after cloning (`slotFrame.componentPropertyReferences = { slotContentId: key }`) — Figma then converts the node back to type SLOT.
- `layoutWrap = "WRAP"` on a COMPONENT_SET works via the API even though the UI hides the wrap toggle for sets (useful to lay out variant grids).

### 🧟 Zombie instances: deleted components and their phantom masters (2026-07-30)

Full component audit of B2C-und-CI: **78 instances hanging on 26 deleted masters.** Everything below was verified live in that audit.

**The "garbage master name" is the deletion signature, not a naming bug.** When a component (or variant) is deleted, Figma keeps a frozen copy as the instance's `mainComponent`. Its name is the **set name + all variant values, slash-joined**:
```
Buttons / LG / PrimaryButton/False/False/False/False
CMS / Editorial/CMS/Editorial/False/False/True/False/False
Full-Size-Element/Default/Nachhaltigkeit/max 1259
Page/-/-
```
Do **not** report these as misnamed components, and never write them onto the instance. Running "set every instance name to `mainComponent.name`" across the file wrote deletion garbage into ~15 layer names before it was caught.

**Decisive zombie test.** `getMainComponentAsync()` returns the phantom, so it is **not** an existence proof (same class of error as the stale variable getter). Build the union of component IDs actually present in the page tree:
```js
const present = new Set();
for (const page of figma.root.children) {
  await page.loadAsync();
  for (const n of page.findAllWithCriteria({ types: ['COMPONENT','COMPONENT_SET'] })) present.add(n.id);
}
// zombie if: mc && !mc.remote && !present.has(mc.id) && !(setId && present.has(setId))
```
Check the parent **set** ID as well — a live variant can sit in a set that is itself gone, and vice versa.

**A swap away from a phantom is IRREVERSIBLE.** Once `swapComponent()` points the instance at a living component, the phantom can no longer be addressed as a target. There is no way back. Before swapping, capture **content, not counts**:

- all `characters` per text layer (keyed by layer name)
- `reactions` as data, not `.length` — one XXS button silently lost its single reaction (1 → 0)
- `layoutSizingHorizontal` and `visible` (restore both afterwards; swap can reset them)

Observed side effects: reactions can also be **gained** (the target master carries its own), and width/height can jump — 240 → 88, 512 → 618, and a content module 216 → 412 in height.

**The phantom's subtree is unreadable — but the axis names may hold the label.** `findAll` on a phantom master returns nothing, so the old label text cannot be read from it. Workaround when the deleted set used **one boolean axis per label** (`"Abkassieren lassen"?`, `"Anmelden"?`, …): the axis whose value is `True` **is** the label text. That was the only way to recover what six buttons said.

**Rebuilding a deleted component from a frozen instance** works and preserves all content — used to restore a nutrition table, an ingredients module and an icon:
```js
const clone = src.clone();            // src = the zombie instance
host.appendChild(clone);
const frame = clone.detachInstance(); // INSTANCE -> FRAME, content intact
const comp  = figma.createComponentFromNode(frame);
comp.name = 'Patterns / NutritionTable';
// two colour states -> one set:
const set = figma.combineAsVariants([dark, white], host);  // parent arg required
set.name = 'Icons / PaperBag';
```
Then `swapComponent()` the remaining zombies onto the new variants. Text overrides survive because the inner layer names come from the same source.

## 4️⃣ LAYOUT

### Flex: creating a frame
```javascript
const frame = figma.createFrame();
frame.layoutMode = 'VERTICAL'; // or 'HORIZONTAL'
frame.itemSpacing = 16;
frame.paddingLeft = 20; frame.paddingRight = 20;
frame.paddingTop = 20; frame.paddingBottom = 20;
frame.primaryAxisAlignItems = 'MIN';
frame.counterAxisAlignItems = 'CENTER';
page.appendChild(frame);
```

### Flex: adding a child (order matters!)
```javascript
// FIRST appendChild, THEN set layoutSizing
frame.appendChild(item);
item.layoutSizingHorizontal = 'FILL';
item.layoutSizingVertical = 'FIXED';
```

### Grid (✅ works — watch for quirks, tested 2026-06-03)

**Correct order (must be followed):**
```javascript
frame.layoutMode = "GRID";
frame.gridColumnCount = 2;       // 1. count first
frame.gridRowCount = 1;          // 2. count first
frame.gridColumnSizes = [...];   // 3. then sizes
frame.gridRowSizes = [...];      // 4. then sizes
frame.gridColumnGap = 40;
frame.gridRowGap = 0;
```

**`gridItemsPositioning` — auto vs manual:**
```javascript
// ✅ ROW_AUTO_FLOW: children are placed into rows automatically (default)
frame.gridItemsPositioning = "ROW_AUTO_FLOW";

// ⚠️ MANUAL: every child needs setGridChildPosition() — often causes unwanted side effects
frame.gridItemsPositioning = "MANUAL";
child.setGridChildPosition(0, 0); // (rowIndex, columnIndex)
```
Recommendation: use `ROW_AUTO_FLOW`.

**Grid frame height — `counterAxisSizingMode`:**
```javascript
frame.primaryAxisSizingMode = "FIXED";  // fixed width
frame.counterAxisSizingMode = "AUTO";   // ✅ height hugs content (needs ROW_AUTO_FLOW)
frame.counterAxisSizingMode = "FIXED";  // ❌ height stays fixed — content can overflow
```

**Full-size grid frame with padding (preferred pattern)** — instead of a small, centered inner frame:
```javascript
// ✅ Clean: grid fills the whole slide, padding creates spacing
frame.layoutMode = "GRID";
frame.resize(874, 595);          // slide size
frame.paddingTop = 78; frame.paddingBottom = 78;
frame.paddingLeft = 78; frame.paddingRight = 78;
frame.primaryAxisSizingMode = "FIXED";
frame.counterAxisSizingMode = "FIXED";
frame.x = 0; frame.y = 0;

// ❌ Cumbersome: a small inner frame has to be centered manually
inner.x = Math.round((slideW - inner.width) / 2);
inner.y = Math.round((slideH - inner.height) / 2);
```

**Rotated text as a direct grid child** (no wrapper frame needed):
```javascript
const heading = figma.createText();
heading.characters = "CONTENT";
heading.fontSize = 63.6;
grid.appendChild(heading);
// After appendChild: y = original text width, rotation 90°
heading.x = 0;
heading.y = heading.width;  // y = text width (before rotation)
heading.rotation = 90;
```

**Allowed types for `gridColumnSizes` / `gridRowSizes`:**
```javascript
// ✅ Allowed:
{ type: "FLEX", value: 1 }    // 1fr
{ type: "FIXED", value: 42 }  // fixed pixel width
{ type: "HUG" }               // fit-content

// ❌ Not allowed (throws an error):
{ type: "MIN_CONTENT" }
{ type: "STRETCH" }
```

**Other grid rules:**
```javascript
console.log(frame.gridColumnSizingCSS); // ✅ read-only, for verification
frame.gridColumnSizingCSS = "...";      // ❌ throws

child.gridChildHorizontalAlign = "AUTO";    // ✅ MIN | CENTER | MAX | AUTO
child.gridChildHorizontalAlign = "STRETCH"; // ❌ throws

child.layoutSizingHorizontal = "FILL"; // ❌ throws for grid children
// ✅ control width via gridColumnSizes on the parent instead
```

**General:** don't set `clipsContent` as a default — only explicitly when needed.

### Mirrored / flipped nodes: diagnosis via transform determinant (2026-08-05)

- `node.rotation` does **not** reveal mirroring — a vertically flipped node reports `rotation: 0`. The only reliable signal is the determinant of `relativeTransform`: `det = m[0][0]*m[1][1] - m[0][1]*m[1][0]` → `det < 0` = mirrored.
- Diagnosis pattern: walk the subtree, flag nodes with `det < 0` or `rotation ≠ 0`, return id/name/transform. Cheap and precise — in the case below exactly one node was flagged (the COMPONENT itself; children untouched).
- Repair: assign `relativeTransform` directly, converting the visual position. For scaleY = −1 the visual top edge is `ty − height`:

```js
const m = node.relativeTransform;          // e.g. [[1,0,20],[0,-1,1937]]
node.relativeTransform = [[1, 0, m[0][2]], [0, 1, m[1][2] - node.height]];
```

  Direct assignment also works on a COMPONENT variant inside a component set (sets are not auto-layout, so no layout constraint interferes).
- A flip on a master component’s **own node** does not propagate to instances — instances render the master’s children, not its transform. Fixing the master is instance-safe; no follow-up instance check needed.
- Visual signature in screenshots: glyphs upside-down and content order bottom-up, while left-to-right order stays intact (scaleY = −1).
- Case: `Components / Search / QueryState` → variant 2394:1332, `[[1,0,20],[0,-1,1937]]` → fixed to `[[1,0,20],[0,1,208]]`.

## 5️⃣ READING & VERIFICATION (API level)

Workflow-level verification (return values, get_metadata, user confirmation): **1.2 §4️⃣**.

- **`findAll` / `findAllWithCriteria` are not stable within one execution** (2026-07-30): identical loops in the same script returned 0 hits and then 19 hits. Collect IDs first, re-fetch by ID, and repeat the pass until a re-scan is stable — do not conclude "already fixed" from a single empty result.
- **`get_screenshot` returns a 1×1 image for hidden nodes** — a hidden node cannot be verified visually at all. Related: Figma does not navigate to a hidden layer via a `?node-id=` link — the selection lands on the nearest visible neighbour, making such links useless for humans. Give the parent variant plus the layer position instead. (2026-07-30. Cowork-specific screenshot download restrictions: 1.2, New findings 2026-07-25.)
- **Visual check inline:** `await node.screenshot()` inside the `use_figma` call; structure via `get_metadata` (XML: hierarchy, counts, positions — no images).
- **MCP reads can be stale** — variables, text styles, `explicitVariableModes` (see §2 "Getters can read stale"); when in doubt, resolve ground truth (`resolveForConsumer`, re-scan) instead of trusting a single getter.

## ⚠️ IMPORTANT LIMITATIONS (quick list)

- ❌ `console.log()` — Claude doesn't see it (use `return`)
- ❌ `figma.notify()` — the user doesn't see it (throws)
- ❌ `figma.root.appendChild()` — use `page.appendChild()`
- ❌ Sync APIs (`getNodeById`, `getLocalVariableCollections`, `getStyleById`) — use async variants
- ❌ `layoutSizingHorizontal` for grid children
- ❌ `instance.reactions = [...]` (read-only) — use `await instance.setReactionsAsync(...)`
- ❌ FLOAT variables bound to `characters` — STRING only (§1)
- ❌ PERCENT `lineHeight`/`letterSpacing` as variables — pixels only (§2)
- ❌ `instance.setProperties({[slotKey]: …})` — populate slots via appendChild (§3)
- ❌ don't set `clipsContent` as a default
- ✅ Variables read/write/create/bind (`VariableID:` prefix required)
- ✅ Text changes (with font loading — §1 for when it's needed)
- ✅ Text style creation (`createTextStyle`, local styles only)
